# Governed assignment recovery boundary

Audience: contributors. This design supports the recovery requirements in [Contracts](../CONTRACTS.md) and the integrated [delivery goal](delivery.md). It is not a whole-workflow qualification claim. Current supported ordinary-root and grant-ceiling recovery is documented in [capabilities](../docs/capabilities.md); native-origin task and operation recovery remain separate work.

## Problem and selected structure

Public cancellation records the original assignment closure, cancels its result dependencies and advances affected work epochs. Restoring the ordinary owner root and renewing its finite lineage grant cannot restore a cancelled child's original actor. Recreating the child or operation loses identity and spends a different allowance. Restoring scalar states alone can instead make obsolete source authority appear usable.

Use explicit same-assignment recovery requested by a genuinely current ordinary coordinator under the same original owner root. Preserve the original task source and invocation. Record new authority as a separate execution-generated event, linked to the complete previous assignment. A single resolver owns effective assignment authority for launch, active ancestry and queue admission; the historical lineage reader keeps its existing responsibility. A current-authority event is not a new source request, model binding, grant or procedure result.

Owner review can authorize recovery, but cannot fabricate a native caller. An operation-scoped owner adoption that drops cancelled task provenance bypasses the prerequisite and is unsuitable. A graph-wide revival has no demonstrated need: recover one exact direct task and leave descendants and dependencies terminal until their own explicit actions.

## Admission and durable result

The initial route covers direct non-context governed assignments whose original coordinator is the same restored owner root. The caller is the host-captured live ordinary native identity, within the root's original project and assignment ceiling. Inputs name the original assignment, expected child epoch, observed child direction and bounded reason. They cannot choose identity, source, work, model or delegation.

Compare original assignment, work, invocation, instructions source, conversation/project and model binding. Require settled child-family producers, cleanup and reservations, valid finite allowances and no pending owner input, goal, native-input recovery or authorized scheduler continuation. A stale source or unknown cleanup holds rather than being inferred safe from cancellation. Existing assignment use is retained; recovery is not another assignment and cannot replenish its ceiling.

The authority event records the actual caller, current owner root/source/epoch, original target and immutable task operands, bounded reason and complete previous assignment. Retain prior recovery links with finite event and byte limits. The owning transaction rechecks its snapshot and archives the old state together with the transition. Unavailable final correspondence rolls everything back.

Restoration records `RECOVERY_READY`, an explicit nonrunning assignment state, and settles the original conversation to IDLE. Launch must reject this state until a separate explicit reentry queues the assignment. Asynchronous launch/completion/error tails must still own the captured authority, cancellation and reentry token before updating it. Advance the child work epoch and generation and retain old governed versions under BLOCKED with planning required; its captured model baseline remains unchanged. It does not schedule a child or parent, clear findings, resolve dependencies, drop history or renew an external operation. A separate existing assignment reentry can resume the same governed work. Preserve its model and allowance, and require current procedure evidence before consequential action. Bound authority history to 64 events, 64 KiB per assignment, 128 KiB per event and 1 MiB of aggregate source bytes. Refuse oversize histories atomically. Existing queued or busy labels cannot substitute for the nonrunning recovery state.

## Later owner direction

Problem: the task source captures only the coordinator's original instructions and the root's initial owner source. Owner input that the root received after the assignment, including input during cancellation, would otherwise never reach the recovered task. Existing inheritance covers only tasks with an effect operation. A forced replan or coordinator-authored reentry text does not deliver the exact owner input.

Alternatives considered: (a) require each reentry to restate owner input: model obedience, not enforcement; (b) a graph traversal or scheduler: unneeded for one direct task; (c) SELECTED: reuse the existing inherited-owner-source record shape for this one recovered assignment.

Selected behavior:

- Source set: root conversation direction revisions after the original caller's `directionRevision` whose source origin is an owner kind. That is the direction when the caller's turn began, so input received during that turn is also held; this errs toward holding. Owner-authored only; parent-child UI relationships confer nothing. Propagation stops when the assignment publishes a COMPLETE result; later effects use existing per-operation inheritance.
- Each source becomes a `DISPATCHED_WORKFLOW` input with mode `inherited-owner-source` on the original target and work, plus a direction row with `effectHold: true`, `classification: 'unknown'` and `inherited: true`. The canonical source ID, exact raw bytes and parent conversation/input/revision are kept. The input also names the assignment, so public assignment cancellation withdraws the dispatch state while its direction stays held.
- Deduplication key: the same work and `inheritedOwnerSource`. Effect-operation inheritance uses the same key in both directions.
- Writers: the recovery transaction itself, a separate `input-queued` subscription registered after effect-operation inheritance (so an operation inheriting the same source still records its own hold or abort; each assignment is isolated), and the launch path before authority validation. All are idempotent.
- Fail-closed reader: the shared authority reader refuses while any source in the set lacks an inherited record. A listener failure keeps the accepted parent input; the next launch retries propagation, and effects ancestry refuses meanwhile. A governed procedure that is already running checks only its own held impacts, so it is not interrupted. Its review-ready result is recorded as UNAVAILABLE with the refusal cause instead of COMPLETE, so completion cannot hide an unheld owner input. The published result carries `assignmentHold`; the route is cancel, recover, then reenter. The recovery pending-input guard ignores inherited `DISPATCHED_WORKFLOW` inputs because their hold lives in the direction row.
- The authority event records the root direction at recovery for audit. Later legitimate root input propagates without another authority event. The recovery receipt returns the updated target direction for explicit reentry.
- Existing `inputDecisions` clears `effectHold` in the direction row after a real adjudicator decision; propagation does not mark anything resolved.
- Bounds apply to sources not yet inherited: 64 sources, 512 KiB per source (the owner input limit) and 1 MiB aggregate. The reader selects only revisions, IDs and byte lengths; raw bytes are read one source at a time when inserting. Exceeding a bound refuses; there is no truncation.

## Consumer obligations

- Launch validates effective task authority while retaining original source/invocation for history. Normal queued launches can outlive their initiating native caller; recovery admission itself cannot.
- Active lineage validates the recovered root and immutable task correspondence. It does not treat parent-child UI relationships as authority.
- Queue admission validates both historical task correspondence and the effective current authority, then obtains current independent procedure evidence through the existing path.
- Historical reads retain their pure original-provenance path. A stale recovery event cannot hide the original from inspection.
- Old integration operations retain their captured grant epoch, origin and alias/dependency obligations. `refreshSourceFit` continues to refuse cancellation/root-epoch changes. A retained native-origin integration has a separate reauthorization route below; task recovery itself never changes it.

## Native-origin integration reauthorization

Problem: an agent integration operation for the recovered task stays REFUSED with a cancelled alias, an old origin token and an old grant epoch. A new operation for the same reviewed assignment and target is not available: the retained operation is selected first, and a replacement would spend a second operation and assignment allowance and lose identity.

Alternatives considered: (a) allocate a replacement: loses identity and spends allowance; (b) owner UI reauthorization plus a later agent adoption: two new states, and the owner cannot supply a native caller; (c) a separate tool: same intent and operands as the integration tool; (d) SELECTED: a narrow branch inside the existing `conversation_integrate` retry path when the retained alias is CANCELLED.

Admission (all required; any failure refuses with no write):

- Caller: the exact live ordinary coordinator whose work is the grant root and the reviewed assignment's original source work. The task's effective authority names the same root and conversation. The current root view must be RUNNING under that exact native actor run and the same work, without an authorized scheduler continuation. Completed historical WAIT handles remain retained and do not themselves refuse admission.
- Provenance: the alias's `cancellationSource` is an `owner-task-cancel` source. The task's latest recovery event restored a previous CANCELLED assignment with the same cancellation source. Agent cancellation is excluded so that a retry cannot undo a deliberate agent cancel.
- Task: COMPLETE again, with current procedure evidence for the current work epoch, which is later than the operation's evidence epoch. The root epoch is later than the operation's origin epoch. No held owner input remains.
- Grant: same ID and ordinary mode, a renewed epoch, and retained history containing the operation's captured grant/root epochs.
- Operation: REFUSED and definitely unsent. No dispatch run, confirmation, transport outcome, or send/preflight/readback/reconciliation receipt, and no active producer. Subject context fingerprints are refused.
- Alias and dependency: exact correspondence to the operation, a single CANCELLED dependency waiting on the caller's conversation, no live alias handle, and fewer than 64 reentries.

Transaction: write an `agent-reauthorization` receipt (actor, cancellation and recovery source IDs, complete previous operation/alias/dependency rows, current grant epochs, evidence, origin and owner-root tokens). Rebuild the operation data from an allowlist (kind, client identity, alias IDs, reviewed assignment, new evidence/epochs/tokens) as PREPARED, so stale projection and authority stay only in the receipt. Run the existing `validate` and preparation-grant checks, append a reentry that names the receipt, and requeue the same alias and dependency. A later fault rolls back all of it. The reauthorization never sends. The requeued alias then follows the normal agent path: queued launch, origin validation, preparation and, when preparation reserves the receiver, the conditional send under the renewed grant and target transmission checks. Owner input on the root after the task completed is not held on the task; like a fresh allocation, it is part of the coordinator's current origin token.

Non-goals: UNKNOWN or INVOKING operations (reconcile only), publication operations, context-bound or override grants, an operation left PREPARED or RESERVED by a crash between cancellation commit and effect cancellation, descendants, and any refund or reset of allowance. The owner-original reauthorization route continues to refuse native-origin operations.

## Required acceptance evidence

Exercise an actual in-process Pi coordinator and public assignment/cancellation paths. Obtain the original governed work through real source capture; if execution stops before the engine or uses controlled procedure evidence, state that limit explicitly. Demonstrate current caller to same assignment/work, metadata-only recovery, explicit same-task reentry, retained model and cumulative use, and current procedure refusal. Test stale and wrong callers, strict/context/different roots, changed instructions/project/model/direction/epoch, pending input or goal, unsettled family or cleanup, exhausted assignment ceiling, duplicate requests, transaction/result rollback and close/reopen. Recovery must not queue descendants, resolve cancelled dependencies, replace IDs or silently reauthorize an existing integration. For later owner direction, verify exact bytes and IDs, single propagation through the subscription, a stale observed target direction, a controlled listener fault with launch-time repair, the aggregate bound for unheld input, cumulative held input above that bound, a controlled completed result that stops propagation, and cancellation followed by repeated recovery. For native-origin reauthorization, use the real assign, cancellation, recovery, renewal and integration tool paths with controlled completion, procedure evidence and source-fit decisions, and execution stopped after queue admission. Verify unchanged IDs and counts, no send, the archived previous rows, and exact refusal causes for an unrenewed grant, an unrecovered task, held input, agent cancellation and possible transmission, plus a later separate task cancellation and recovery whose cancellation differs from the one that withdrew the alias, late-fault rollback and a duplicate request. Source-fit consumption of inherited input uses the existing ChangeCore path; these tests stop before it. The supported direct-root and single direct-inherited recovery profiles also have separate actual-engine and fresh installed consumers. Those consumers preserve original task identities and cumulative usage through current procedures and an owned endpoint. The direct-root consumer separately preserves and reauthorizes an existing native-origin integration. The inherited profile recovers the task before its first native operation and excludes native-operation-bearing tasks. The focused source cases above retain their controlled-evidence limits; installed qualification does not generalize to arbitrary nested recovery, repeated reentry, later producer cuts or live-provider judgment.

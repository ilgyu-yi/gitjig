# Usage

Run `gitjig --help` for the complete command schema. See [Installation](installation.md) for source and prepared-bundle setup. Source invocations use `node dist/cli/entry.js` in place of `gitjig`; an owned installation supplies its own launcher.

## Project and runtime

Enter your request directly when the conversation is configured. Missing model/account configuration or active project-runtime settings appear with a repair command on the conversation screen. Use `/ready` or Ctrl+G then T when setup is needed or to inspect configuration and choose the next action. It distinguishes the current conversation model from future defaults, and the active runtime from saved-next-launch settings. `/setup runtime` edits common execution fields without JSON; advanced bridge/resource configuration remains in [Startup setup](startup.md).

`/project` selects or registers the project for the current conversation. Registration starts with the directory from which you launched gitjig, including when Claude bridge startup uses a separate private working directory. Correct an invalid directory or project identifier in the same registration flow; the entered values remain available until you cancel. Registering a project and changing the current conversation's project are separate outcomes: if retained work holds selection, the new project stays registered and its work-recovery guidance remains available.

For a new conversation with missing setup, the editor shows **Setup needed**. Write your request and press Enter to choose **Open setup** or **Return to request**. The request stays in the editor exactly as written; returning from setup never sends it automatically. Send it explicitly after configuration is ready. Existing work, goals and retained sent requests continue to use their original recovery controls.

Once setup is complete, `/ready` offers **Choose how to give your request**. Choose **Return to conversation · write a prompt** to keep your draft and write naturally, or **Managed task · review a request before starting** to open the explicit task form. **How prompts and managed tasks work** explains both routes. Choosing a method sends no request; a prompt is sent from the conversation, and a managed task starts only after its separate review and confirmation. Existing work, goals and retained requests keep their own next-step recovery paths.

`/ready` opens a short overview of the next action and current project, model, account and relevant runtime. Open **More settings and details** for future model defaults, saved runtime and startup settings, bridge details, language and local/repository tools. **Back to current setup** returns to the overview; **Return to request** closes it. These navigation choices keep the request and do not start work. Repairs and restart instructions remain visible in the current overview when needed.

The row above the editor shows request preparation, queued input, response activity and cleanup, with elapsed time during work. Native output distinguishes thinking, response text, tool execution and retries. A “No new output” duration reports silence; it does not prove that the provider is healthy or has failed. Escape interrupts the current response. Pending sent requests remain available through `/inputs`; a completed response is separate from task completion.

To leave and keep an unsent request, press Ctrl+G then Q. Use your configured command key in place of Ctrl+G. Gitjig saves the draft and waits for owned work to settle before closing. Ctrl+D leaves only when the editor is empty. `/quit` is also available as a command.

Keep the canonical application home outside registered projects. In the UI, use `/project` or Ctrl+G then J to select a registered project or register a directory and ID. Selection applies to the current conversation and retains its history and draft. Active work, pending input or an unfinished goal can prevent a scope change; registration remains saved if attachment is refused. Project selection does not grant execution or repository permissions.

The command-line alternative is:

```sh
gitjig project register --home /absolute/gitjig-home --id example --root /absolute/project
gitjig local inspect --home /absolute/gitjig-home --project example
```

Read-only local inspection does not require a model or engine. Save execution setup once with `gitjig setup save --file /absolute/private/setup.json`; see [Application startup setup](startup.md). A complete invocation override requires an absolute trusted `--docker-binary`, an explicit `--docker-context`, and an immutable `--image sha256:…`. Optional `--docker-config-directory` selects its Docker configuration directory. The override replaces the whole saved runtime. The selected backend must enforce the required work/scratch mounts, protected paths, execution restrictions and cleanup. The separate Interactive runtime installer can prepare Colima and build the image; metadata editing and Save alone do not create an engine. See [execution images](runtime-image.md).

`doctor` reports missing prerequisites. It does not provision a daemon or certify restriction enforcement. Without an engine context, `doctor` checks application prerequisites. With `--docker-context NAME`, it also requires a reachable engine. Colima is one tested backend; Docker-compatible backends must satisfy the same execution restrictions. See [Capabilities and limits](capabilities.md).

## Models and credentials

Gitjig stores application preferences, accounts and models in its own home. Stock Pi settings and credentials do not configure this application implicitly. Account and catalogue commands work without an execution engine or a model turn:

```sh
gitjig auth status
gitjig auth login --provider PROVIDER --method api_key
gitjig auth logout --provider PROVIDER
gitjig models list
gitjig models default --provider PROVIDER --model MODEL
gitjig models scope --patterns '["PROVIDER/MODEL"]'
gitjig models roles
gitjig models role-set --role reviewer --provider PROVIDER --model MODEL --thinking high
gitjig models role-reset --role reviewer
```

Login also accepts `--method oauth` where Pi offers it. Logout removes the application's stored credential; it does not claim upstream token revocation. Model discovery describes the catalogue, not provider entitlement. Use `models configure --file ABSOLUTE_PRIVATE_JSON_FILE` for admitted compatible endpoints and `settings inspect` to inspect effective preferences. UI equivalents include `/login`, `/logout`, `/accounts`, `/model`, `/model-default`, `/scoped-models`, `/thinking` and `/role-model`. Cancelled dialogs preserve the command draft. `/scoped-models` offers staged catalogue/pattern additions and indexed removals. Save applies the application cycling pool; Cancel keeps the old file. Pi patterns, wildcards and `:thinking` suffixes remain supported, and a direct JSON array is available for advanced use. An empty pool makes `/model-next` unavailable. Scope does not change current choices or model defaults.

`/settings` offers plain boolean, enumeration and numeric values. Model defaults open the paired model picker; `/settings modelThinkingLevels` stages per-model requested levels and reset operations. Entries for models no longer in the catalogue can still be removed. Reset removes the application entry. Project overrides are shown separately and can remain effective after an application save. A changed preference file or conversation during editing requires reopening the form. Explicit `/settings KEY JSON_VALUE` remains available for advanced values.

Role overrides apply to future role launches. An unset role inherits that work's captured model baseline. They do not change a dialogue's selected model, an existing work baseline or a running binding. A new `change start` without `--model-profile` captures the application default; a paired `--provider` and `--model` selects an explicit application baseline, with optional `--thinking`. Existing application work resumes using its retained baseline even if the global default changes. It rejects a conflicting `--model-profile`.

For a managed task with mixed verification duties, the accepted plan can distinguish behavioral cases, an original pre-edit baseline observation and complete file-scope evidence. The application runs the required base check before admitting an editing producer. A successful baseline harness demonstrates its declared subject defect; it does not mean the application was already correct. Scope comparison and required independent review remain separate. Inspect the original check/evidence IDs and blockers when verification is unavailable. Resume preserves the work, old failures and spent allowance; it cannot manufacture a missing historical baseline or replace required evidence with reviewer prose. A new typed plan keeps typed accounting on later replans. Mechanical nits currently use ordinary repair and fresh verification/review, so the original finite allowance may stop the work before the extra review; no silent extension or usage reset follows.

Plain `change prepare` remains model-free and requires an explicit profile when later driven. Add `--model-source application` to capture an application baseline during preparation. Existing work without an application baseline cannot silently acquire current defaults: supply its explicit profile. Project execution still needs saved setup or complete runtime operands.

Explicit external model profiles are owner-only JSON files outside registered projects. Preserve the existing credential store; do not put credentials in a project repository. The selected OpenAI OAuth form is:

```json
{
  "provider": "openai-codex",
  "modelId": "gpt-6.1-sol",
  "native": {
    "kind": "pi-oauth",
    "authPath": "/absolute/private/pi/auth.json"
  }
}
```

The profile reuses the specified existing Pi OAuth login. The profile and referenced credential file must be canonical owner-only regular files. Missing credentials refuse with a recovery message; there is no automatic model or account fallback.

Claude uses the explicit `claude-bridge/claude-opus-5-5` selection and `installed-claude-bridge` native profile. That profile also declares private startup directories and a pinned executable. Use [Startup setup](startup.md) for its directories, executable identity and fixed configuration. Merely installing a bridge does not grant project or repository authority.

See [provider integration](providers.md) for account modes and provider-specific limits.

## Conversations and managed changes

The UI entry is `conversation ui --home PATH`, optionally with an explicitly selected external `--model-profile FILE`, with optional `--conversation ID` or `--project ID`. Opening the UI requires no model or engine; executing project work requires the runtime setup described above. The source/npm launcher selects its owned temporary directory automatically. Source commands are:

```sh
node dist/cli/entry.js setup inspect --home /absolute/gitjig-home
node dist/cli/entry.js conversation ui --home /absolute/gitjig-home
```

The installed launcher supplies its bound home and artifacts directory automatically. The source home is selected by `--home`, then `GITJIG_HOME`, then `~/.gitjig`.

Without routing options, gitjig opens the last conversation you selected. If it was archived or deleted, gitjig opens the most recently used accessible conversation; if none exists, it creates one. Opening preserves its draft and model choice and does not resume work. The notice and retained status show this distinction. Use `/resume` or Ctrl+G C to choose another conversation, and `/new` to create one. `--conversation ID` selects an exact existing conversation; `--project ID` or an external `--model-profile FILE` without a conversation creates a new context. An existing external-model conversation can be inspected without its profile; execution requires the matching profile or deliberate model selection.

Use `/new` or Ctrl+G N to open an independent conversation. From a project conversation, choose Current project or Unbound control conversation; `/new project` and `/new root` select these directly. Without a current project, `/new` opens an unbound context and `/new project` asks you to select a project first. New conversations use the selected scope's saved model defaults. Their header shows the actual project/model before execution. Existing histories, drafts, work, goals and obligations remain with their original conversations.

Use `/help` or Ctrl+G then `/` to search all registered commands. Enter runs the selected action through its normal dialogs; Close or Escape runs nothing. Arguments shown in the list describe the command syntax. Existing Ctrl+G letter navigation remains available. Menu-based discovery preserves your editor draft, including text that looks like a slash command.

Use `conversation list` and `conversation inspect` to identify the intended conversation. The conversation picker selects a different conversation; the history picker selects a branch within the current conversation. An unrelated project conversation can require a different runtime profile.

You can give requests in your preferred language. Agent progress, clarification questions and final replies use your conversation language; you can explicitly request another reply language. Agent working records, internal task reports and review results use English and retain the original request alongside its interpretation. English automatic continuations do not change your reply language. Use `/language ko`, `/language en` or another language tag to save this conversation’s reply-language default; `/language` opens its field and explains scope. The saved choice applies from the next model request and survives compaction and restart. `/language auto` returns to interpretation of retained human input. A new explicit request for one response can override the default without changing the saved setting. Context clone/fork copies the preference; unrelated conversations keep their own. Code, paths, quoted source and requested localized product content keep their intended text.

Supported interface copy follows a fixed Korean or English reply-language choice, including regional tags such as `ko-KR` and `en-GB`. In `auto`, the model interprets your human conversation while the interface uses the system locale captured at launch (`LC_ALL`, then `LC_MESSAGES`, then `LANG`, then the host locale). `C` and `POSIX` use English. Other reply/system languages fall back to English interface copy while keeping your reply-language preference. `/ready` and `/language` show the interface source. If your conversation is Korean but the system locale is English, use `/language ko` for Korean labels. No model call or character-based language guess selects UI copy. See [Capabilities](capabilities.md) for the current translation scope.

An assigned agent submits its English result with `conversation_report` and answers you separately in your conversation language. The coordinator reads the report, not your final reply. Missing or stale reports leave the assignment unavailable; they do not turn your reply into a successful internal result. History navigation, compaction and native Bash do not replace a completed task's report.

Use `/change`, or select Managed changes in `/ready`, to find retained work across all projects. You can filter to the current project, page to older/newer work, refresh, and open a scrollable detail view. List rows show the recorded phase; detail shows the current assessed state, next action, original request/model and consumed/reserved execution and resolution allowances. Selecting a work item does not run it or change the draft. `/change inspect WORK_ID` opens a known item directly. Choose Start a new managed change, Resume a retained change or Cancel a retained change for an explicit action. `/change start REQUEST`, `/change resume WORK_ID` and `/change cancel WORK_ID` are direct forms. Resume and cancel can also find the work through the registry without an ID.

Use `/result` or Ctrl+G then R to read the current managed task's result: saved candidate location, changed paths, checks for the selected candidate and verification plan, and attributed review evidence. Without a linked task it opens a result picker, initially scoped to the current project. `/result WORK_ID` opens an exact task; `/work` also offers **View result**. Opening a result runs no work and applies no files. Locations and changes are retained records, not a fresh comparison with the original folder. Publication, integration and PR merge records remain separately available through `/repo`. A review-ready candidate does not imply a completed delivery. Large result sections disclose omitted entries; CLI `change inspect` retains the full procedure records. Conversation notifications remain available through `/notifications` and F5.

Start uses the selected project and current conversation model, not the future application default. Enter a request in the form or explicitly select a non-command editor draft, including a multiline draft. Confirm the project, model and request before dispatch. Acceptance starts background work; it does not report completion. Its source view shows recorded progress and the settled result. You can navigate while it runs; errors remain with that source and are available in `/error`. A submitted command clears after admission if it is unchanged. Menu actions preserve the editor draft.

Resume keeps the original work, project, model and spent allowances. If the original source is another conversation, the UI offers to open it and continue to its resume review. Navigation starts no work: confirm the fresh review in the original conversation to resume, or cancel there. Both conversations retain their drafts. Recovery of cancelled/interrupted work requires explicit confirmation. Cancel names the work and delegated executions it covers. It retains history and cleanup obligations and does not undo prior external effects. Closing gitjig stops and joins its managed operations before releasing account resources. Runtime/model execution still requires the configured prerequisites; a successful confirmation alone does not prove their availability.

The command-line registry is `gitjig change list --home PATH`, with optional `--project ID`, `--limit 1..100` and `--before WORK_ID`. The returned `nextCursor` selects the next older page. Listing works without a model or engine and bypasses saved startup configuration, including invalid setup. It does not reconcile interrupted work or reset allowance. Use `change inspect` for a selected work's current detail.

If owner-delegation activation fails after a change is created, keep its reported work ID. Restore the original `--delegate-integrations` and `--delegate-publications` selections, then run `gitjig change activate --home PATH --work WORK_ID --epoch CURRENT_EPOCH` with those selections. Integration selections also require the explicit `--git-binary` profile. The command installs both grant families together and reports the same work; it does not run a model, load saved runtime/bridge setup, dispatch an external action or reset allowances. A different profile is refused. If capture or cleanup is unfinished, first reopen normally to reconcile its retained run, then inspect the current epoch. Unknown cleanup must be resolved before activation. For cancelled/interrupted pending work, add `--resume-cancelled true` only when you intend to make that original work active again. Execution remains a separate explicit action. Repeating completed activation preserves the original grants and usage. Work created before captured activation profiles uses its existing explicit recovery route.

A managed implementation starts with `change start` or resumes through `change run`/`change resume`. It requires registered project, owner request, model and runtime inputs. Planning, independent challenge, implementation, meaningful checks and independent review retain one work identity and finite allowances. `change inspect` reports the actual endpoint. A review-ready result does not imply publication or merge permission.

After viewing `/result`, a separate **Review branch delivery for this result** action keeps that exact work and project while opening the existing receiver, delegation and preparation controls. Back performs no action. An existing original integration stays the recovery target; the flow does not silently select another work. Branch delivery, issue/PR publication and PR merge remain separate endpoints, and their current authority checks and explicit confirmations still apply.

Use `/work`, Work recovery in `/ready`, or Inspect linked work and budgets in `/goal` to find original ordinary, child or managed work. Current conversation and goal-linked work appear first; the all-project registry remains available. `/work WORK_ID` opens a known work directly. Inspect its original request, state, next action and shared-lineage counters. Finding occurrences and diagnostic obligations have separate paged lists with attributable details. A newer review does not erase an earlier occurrence. Large detail is explicitly shortened; CLI `work inspect` or `change inspect` retains the original record.

If a managed change stops because gitjig's installed workflow rules have changed, open `/work WORK_ID` and choose **Review updated gitjig workflow rules**. Review the affected files and selected clauses, enter an owner reason and explicitly adopt the reviewed version. The review distinguishes changed rule text from changed source-file identity and can show the complete retained and current selected clauses. Project requirements and goal criteria stay the same. The candidate, findings, history and spent allowance remain; accepted planning, verification and review selections are cleared. Independent planning must adopt the new rules, and resuming remains a separate action.

New ordinary conversation families and standalone managed changes start with 32 execution units and 8 resolution units. Ordinary-to-managed transitions share the original family allowance, including its spent usage. Retained limits and explicit managed limits are preserved. If the allowance is exhausted, open `/work WORK_ID`. Choose Extend shared execution allowance or, for governed work, Extend shared resolution allowance. Enter 1..100 units and an owner reason, then confirm the original work, current/next limit, used/reserved counts and shared scope. Other work in that lineage and later continuations use the same allowance. Goal turn allowance stays separate. A changed or busy lineage requires fresh inspection; unsettled cleanup requires reconciliation first. Extending retains consumed usage and findings and does not resume execution. Use the original `/change` or `/goal` controls, or CLI `work resume`, for a subsequent explicit execution action.

Ordinary owner and delegated investigation work have a **Review cancellation of this original work** action in `/work`. Read the exact work, source and cancellation scope; **Back without cancellation** is the default. Cancellation uses the original work and epoch, preserves history and spent allowance, and does not undo external effects. A new direction or changed source during review requires a fresh review.

Old structured-result callbacks could leave a result wait pending after an accepted completion. An explicit resource reclaim (including a reviewed project change) can reconcile an original outcome only when its retained publication and source/recipient records prove the correspondence. It runs no model and creates no result or procedure standing. Changed-source historical reentries and incomplete evidence remain held for original inspection or explicit cancellation. A false COMPLETE label with no accepted publication is never treated as success; explicit cancellation retains the previous label and history while withdrawing its pending wait. Completed, resolved historical assignments remain unchanged.

If a project change is held by a delegated task that has not started and has no work ID, open `/error` in its coordinator or task conversation. **Review cancellation of unstarted delegated task** shows the exact task, queued request and result wait. Back leaves it unchanged; explicit confirmation cancels only that task and its queued request. Parent and sibling work, existing parent continuation intent and any cleanup obligations remain. Then choose your next action separately. Already admitted or ambiguous tasks show a hold and keep their original work recovery; do not reset the application merely to clear a queue.

Coordinator status distinguishes an idle conversation from its cancelled work or assigned task. A new request to wait for a cancelled or unavailable original task returns its outcome and recovery guidance without ending the current turn. A completed label with no readable original result also requires inspection instead of waiting. Recovery remains a separate explicit action on that original task. Restoring admission does not start the task; it still needs explicit reentry before waiting for its result. An idle conversation alone does not establish readiness to resume it.

For a cancelled or interrupted ordinary owner conversation, select its original work and choose **Review original conversation admission recovery**. Enter an owner reason, read the full review and confirm **Recover this original conversation admission**. The default is **Back without recovery**. This restores the same independent owner's work without running a model or renewing a grant. A settled cancelled wait is archived and its automatic continuation is disabled. A previously consumed continuation left in older state can also be archived when its original wait, successor and result records prove that it was consumed; arbitrary inactive flags cannot clear it. In either case, its cancelled children, dependencies and unresolved obligations remain. Open the original conversation and submit a separate ordinary input to continue. Physical history verification is pending until that input is dispatched; missing or changed history still refuses. Pending inputs, goals, unsettled cleanup, changed history/session pointers and delegated/context work remain held. This entry is distinct from CLI `work resume`, which handles investigation and command work. Existing ordinary lineage ceilings have a separate reviewed [grant-renewal route](integrations.md#renew-authority-after-original-work-recovery). Restoring admission does not renew them. Owner-route reauthorization of native-origin integrations remains unsupported; renewing a ceiling does not restore old native, assignment or context authority.

After restoring an independent original ordinary root, use `/work` on an already admitted direct clone/fork and choose Review retained context admission recovery. Enter a reason, review its original source, ceiling, shared allowances and history checkpoints, then explicitly confirm; Back is the default. Gitjig verifies both retained native histories before restoring that same context admission. Missing or changed history, unfinished cleanup, pending input/goal or unrelated assignments keep it held. This action runs no model and creates no task, grant or send. Continue with a separate input afterward; renew any stale original grant separately in `/repo`. Old descendants stay held, and another root cancellation invalidates the restored context. Nested contexts, cancelled inherited assignments and changed source-root identity require their own recovery.

A direct clone/fork coordinator that was explicitly cancelled while waiting for one original inherited task can use the same `/work` recovery action. The review identifies the cancelled task and wait. Recovery archives and withdraws only that wait; the original task and dependency stay cancelled. In the restored coordinator conversation, ask it to inspect and recover that exact original task with `conversation_status` and `conversation_recover_assignment`, then inspect the target again before explicitly reentering it with `conversation_assign`. A new owner input may advance the target direction. No replacement task is created. Nested contexts, multiple waits, previously recovered/reentered tasks and tasks with native operations remain held.

If that original inherited task lost its process during initial implementation, restore its selected runtime and reconcile its owned execution before recovering the coordinator. Preserve its interrupted run, native history, partial staging and findings. Missing producer history blocks replacement; restore the exact file before explicitly retrying the same assignment. Replanning and endpoint review consume additional allowance. Use a separate reasoned `/work` allowance extension when needed; recovery does not reset prior use. This route covers the initial implementer before an accepted candidate, not arbitrary later cuts or uncertain external sends.

A cancelled governed task that the root coordinator assigned is not restored with its root. After you recover the root, ask its coordinator in that conversation to recover the original task. The coordinator first uses `conversation_status` on the original assigned conversation to observe `workEpoch` and `directionRevision`, then supplies those values, the original assignment and a reason to `conversation_recover_assignment`. A conversation without bound work reports a null work epoch; inconsistent bound-work metadata is refused. Recovery rechecks the observed values against current authority before mutation. Only a direct, non-context task of the same root, with settled producers and cleanup and no pending input or goal, qualifies. Recovery keeps the original task, model and allowance use, and it does not run the task. Your messages to the root since the coordinator turn that made the original assignment are attached to the task exactly as you wrote them, and they stay held until an independent source-fit decision accounts for them. Later root messages are attached in the same way until the task publishes a completed result. The coordinator must then explicitly reenter the same assignment with the returned direction revision. Recovery does not restore cancelled dependencies or descendants and does not reauthorize an old integration operation. If the task had an unsent integration that your cancellation withdrew, first renew the original grant in `/repo`. After the recovered task completes again with current procedures, the coordinator can request integration of the same task and receiver again. Gitjig then reuses the same operation and allowance, records the change and queues that original integration again. It then follows the normal agent integration path, which prepares it and can send it under the renewed grant, exactly as a new agent integration would. Messages you send to the root after the task completed are part of the coordinator's current request, not held on the task. An operation with any possible send must be reconciled instead.

After process loss during an initial managed implementation, reopen the original application home with its selected runtime setup. If that runtime is unavailable, retained cleanup stays UNKNOWN; reopening a record does not certify that the execution scope stopped. Restore the exact Docker configuration/context route before reopening to reconcile its owned journal. Keep the original work and its partial staging/history. Missing or changed checkpointed native history still holds execution; restore the exact retained session rather than substituting another producer. Then explicitly resume that same managed work through `/change resume` or `gitjig change resume --work WORK_ID`. Once the interrupted first author is accounted for, a work with no accepted candidate runs normal planning again before implementation, effective checks and independent review. These are new charged attempts under the remaining original execution/resolution allowances. Earlier work, raw diagnostics and spent attempts are preserved. Other interrupted stages, context-derived tasks and uncertain external sends keep their own recovery requirements.

If `/ready` reports an original startup cleanup hold, open the named `/work` and choose **Review failed startup cleanup**. When the retained original Docker response proves that its exact bind source was rejected before container creation, review and confirm recovery of that same startup. This releases its quarantined capacity while retaining the work, requests and spent allowance. Then open `/inputs` in the original conversation to choose safe retry or withdrawal. The action does not retry a request, renew a grant or clear an uncertain native execution. Other unknown creates still require their original runtime evidence; a missing container on today's selected daemon is insufficient.

If a process stops after deleting its container but before saving that cleanup, normal reopening can recover a known full container ID when its original daemon binding was already saved and a complete current native inventory proves it absent. Restore the original Docker setup first. Missing daemon access, a different daemon, legacy records without that binding and uncertain name-only creation remain held; an inspection error alone does not prove deletion. Recovery retains the spent attempt and does not turn its check into a pass. Explicitly retry the original work for a new result.

Owner scope changes and allowance extensions use explicit commands with recorded reasons. Retrying or reopening does not reset consumed allowance or erase unresolved findings. Unknown external effects require reconciliation before another send.

## Local checks and repository rules

Use `/local` for selected-project Git status/history, plain convention fields, staged preparation, isolated checks, retained original-check continuation, candidate recording and historical commit audit, or the CLI entries in [Local development](local-development.md) to configure branch/commit-message conventions and prepare staged changes without an agent task. `local recommend` prints optional rules; `local configure` applies an explicit profile at the inspected revision. `local prepare` checks those rules and reports each outcome. It does not commit or substitute for tests and review.

Use `gitjig local git --home /absolute/gitjig-home --project example --git-binary /absolute/trusted/git` to inspect a registered Git worktree. The JSON result separates index and worktree status, retains rename origins and untracked/conflicting paths, and lists up to ten recent commits. Unborn and detached branches have explicit states. Register the exact canonical worktree root; linked worktrees are supported. This command works without a model, execution engine or valid saved startup setup.

Keep repository configuration stable and stop configuration-changing tools during inspection. This native Git entry is not an execution sandbox. Preflight refuses configured clean/process filters and partial-clone/promisor routes, but a concurrent configuration replacement can introduce a helper before a later drift refusal. That refusal does not prove that no helper ran or external action occurred. Use trusted Git directly for unsupported repositories. With stable configuration, inspection leaves the index, branch and work files unchanged. It issues no fetch, stage or commit command and does not approve a change. Submodule contents and ignored files are excluded; upstream names are local observations. Non-UTF-8 output, incomplete output, more than 1 MiB per command, commands exceeding five seconds, and observed drift refuse with recovery guidance. The observation is not an atomic snapshot; inspect again after further edits. A general commit/push gate remains unavailable.

`local check` runs a supported actor-neutral check with its explicit project/runtime inputs. It does not require an agent plan or review transcript.

Use `local evidence --project ID --work W --git-binary /absolute/trusted/git` to compare original successful /work command evidence with a fresh full source capture and staged raw blobs/modes. CURRENT is source/index correspondence, not test adequacy or commit authorization. STALE preserves the old result as history. Missing/uncertain/scratch-dependent evidence refuses. See [Local development](local-development.md#inspect-check-correspondence) for input scope, recovery and the remaining commit boundary.

Use [Repository inspection](repository-inspection.md) for model-free GitHub.com, Gitea and GitLab native observations. For native existing-setting updates and explicit protection creation, use [Gitea/GitLab configuration](repository-configuration.md). Those native profiles remain separate from the GitHub configuration paths below.

Use `/repo` (also linked from `/ready`) for target registration, explicit current branch-policy observations, staged common settings, retained-plan inspection and explicit preview/apply/audit/reconciliation through the existing journal. Credential prompts ask for a private file path, not token text. See [repository configuration](repository-configuration.md#use-the-terminal-interface).

Use `/repo register` to open repository registration, `/repo targets` for registered identities and resource tracking, `/repo integration-targets` for source branch targets and registration, and `/repo merge-targets` for PR targets. `/repo merge OPERATION_ID` opens one retained PR merge's original recovery controls. These entries preserve each operation's existing reviews, credentials, authority and confirmation requirements.

Use `repo register-target --home HOME --provider github --owner OWNER --repo NAME --credential-profile FILE` to observe the current GitHub User/repository IDs and visibility without writing target JSON. GitHub remains fixed to GitHub.com; a custom API base refuses. For Gitea/GitLab, supply their explicit canonical HTTPS `--api-base`. Alternatively retain the private `--target-profile FILE` entry, without mixing provider flags. Registration stores an identity and does not activate configuration writes or establish authority. `repo targets --home HOME` and `repo plans --home HOME [--target TARGET_ID]` discover retained records without dispatch or recovery. See [configuration discovery and recovery](repository-configuration.md#find-retained-targets-and-plans).

GitHub `repo recommend --branch NAME` prints an editable recommendation without credentials or mutation. Customize its supported settings, then use the owner-only `repo preview`, `repo apply`, `repo audit`, `repo reconcile` and `repo guide` commands. Preview, observed state and effective guidance remain distinct. Private configuration and credential profiles stay outside registered projects.

The GitHub native mutation adapter is limited to the declared public, personal-user-owned, nonfork GitHub.com profile. Private, organization and app profiles retain their explicit read/preview or unavailable limitations. Internal same-account review is not a separate-account GitHub approval. Ordinary landing and discretionary override require their actual corresponding account authority and explicit delegation.

## Installation lifecycle

Use [Installation](installation.md) for prepared-bundle staging, activation, recovery and removal. The installed bundle launcher's `gitjig health` checks assets; `gitjig health --loaded` checks the loaded SDK. Source and npm installations do not provide `health`. Health does not grant task or repository authority.

## Noninteractive input limits

Use the existing structured `conversation start --project ID --message TEXT` and `work resume --work W --message TEXT` commands for selected-project investigation and retained work. Their execution prerequisites and workflow gates still apply. The parser accepts named option/value pairs; it does not read stdin, accept positional prompts, `--message=...`, or an option terminator (`--`). An option value beginning with `--` is refused. Projectless dialogue is available in `conversation ui`. A projectless goal can also run through the explicit `goal run`/`goal resume` workflow. Generic positional-prompt print/one-shot aliases and Pi JSONL/RPC compatibility are not supported.

## Persistent objectives

Use `/goal create` in a conversation to define an objective and completion criteria, then `/goal start` to begin. Goal state, progress and consumed allowance survive restart; execution resumes only by an explicit owner action. See [Goals](goals.md) for the UI and command line.

## Entry errors and recovery

A home error identifies the affected path. `FOREIGN_HOME` means the nonempty directory has no recognized ownership marker, or its marker cannot be verified. Inspect its contents before changing anything. Do not invent a marker or delete existing files to bypass the check. To use a separate home, select a new dedicated directory:

```sh
gitjig conversation ui --home /absolute/empty-gitjig-home
```

`UNOWNED_STATE` identifies an unsafe type, owner, permissions or noncanonical directory. If a parent path is an alias, inspect the reported resolved path and use the canonical application home. A state or artifacts subdirectory is not a replacement application home. Leaf symlinks remain unsupported. `OWNER_BUSY` means a controller or unresolved ownership record still holds the home. Close the live controller; verify its producer has stopped before explicit maintenance. Do not delete a live owner's records.

In the UI, `/error` or Ctrl+G then E opens recovery choices for the last captured failure in the selected conversation. Choose **Error details** for a scrollable inspection that includes supplied recovery guidance and work/run IDs. Up/Down scroll, PageUp/PageDown page, and Enter/Escape close. Inspection does not retry work, extend an allowance or change the draft. Ctrl+G E also works when a draft cannot be saved; a failed command alone does not mean the draft is unsaved. Details are local to the current UI view cache; retained work remains available through its normal inspection commands after restart. Very large display fields are shortened explicitly.

## Choose recovery after an error

Recovery screens offer entry points to existing controls. `/ready` opens `/work WORK_ID` for retained managed work. `/error` can open the original work, pending inputs or the conversation goal even when a stopped operation produced no exception text. Local-check, publication, integration and PR-merge screens link their original work to allowance and cleanup inspection; entering these controls does not retry or send. Missing projects, repository identities and source branches offer their existing registration screens. An empty `/goal` inspection offers goal definition without starting execution.

Cancelling a prerequisite registration returns to the staged form while its conversation and project remain unchanged. Cancelling a nested action in `/ready` returns to the overview; earlier saved changes remain applied. Work lists show status and request text before long identifiers.

External storage repair, original private profiles, native authentication and remote CI still need their stated external actions; an entry point does not certify that a blocker has been resolved.

Open `/error` (or the command key then E) to choose **Error details**, **Open setup and readiness**, or **Review retained sent requests** when a request is retained. Opening this menu sends nothing and does not retry work. Details remain read-only; Escape returns directly to the conversation. Readiness enters the applicable setup choices. Retained-request review uses the existing exact-request confirmation before retry or withdrawal. Newer errors or changed conversation/model scope invalidate an open recovery choice; reopen it for current information.

A request can be **Not sent to model · recovery held** when its failed startup is settled but earlier managed work still needs attention. `/inputs` shows the retained failure and current holds, and offers **Inspect blocking work** for that original work. Inspection does not retry, withdraw or resume anything. In the work menu, choose **Review managed change** to read its retained failure; closing the details returns to the same menu. **Review resume** and **Review cancellation** open the existing confirmation for that exact work. The rows also show runnable chat commands, such as `/change resume WORK_ID`; `/work WORK_ID` opens the recovery menu directly. Fix the retained cause before confirming resume, which can use model credits and remaining allowance. Cancellation retains history and cleanup obligations. Review the held request again through `/inputs` after the original blocker is resolved.

Project capture includes Git-ignored files. If a capture error identifies a temporary evidence link outside `node_modules`, move that evidence outside the project while preserving it. Ignoring it in Git does not exclude it from capture. Functional source links require a supported project layout. After fixing the reported path, explicitly retry the retained request or resume the original managed work; do not submit a replacement to bypass it.

For retained managed work, `/ready` offers recovery actions for the original stage provider or bridge. If settings are held, inspect the same original work or review cancellation and its effects on delegated executions. Cancellation does not guarantee settings become writable and does not undo previous effects. Resume remains a separate reviewed action; recovery does not select a replacement work/model. For an ordinary conversation with a missing Claude bridge, choose bridge setup or explicitly select another current model.

# Usage

Run `gitjig` in an interactive terminal to open the conversation. Use `/ready` for setup and next steps, and `/project` to select or register a project. If your request starts running while `/ready` is open, selecting the old recommendation refreshes the menu and asks you to choose again. Changes to its task or prerequisites can also refresh the recommendation. Escape returns to the conversation. Run `gitjig --help` for the complete command reference. See [Installation](installation.md) for source and prepared-bundle setup. Source invocations use `node dist/cli/entry.js` in place of `gitjig`; an owned installation supplies its own launcher.

## Project and runtime

Enter your request directly when the conversation is configured. Escape can stop the current response while its interrupt hint is visible. Once the response enters cleanup, the status shows that it is finishing. Normal exit waits for cleanup and keeps the outcome the response already reached. A conversation without a project can answer questions using its selected model before Docker is set up. Missing model/account configuration or active project-runtime settings appear with a repair command on the conversation screen. Use `/ready` or Ctrl+G then T when setup is needed or to inspect configuration and choose the next action. It distinguishes the current conversation model from future defaults, and the active runtime from saved-next-launch settings. `/setup runtime` edits common execution fields without JSON; advanced bridge/resource configuration remains in [Startup setup](startup.md).

`/project` selects or registers the project for the current conversation. If you abandon registration, the project list reopens so you can choose an existing project or close it. Registration starts with the directory from which you launched gitjig, including when Claude bridge startup uses a separate private working directory. Correct an invalid directory or project identifier in the same registration flow. The entered values remain available until you cancel. Closing before folder validation finishes cancels the pending registration. Registering a project and changing the current conversation's project are separate outcomes: if retained work holds selection, the new project stays registered and its work-recovery guidance remains available. The activity row shows the held destination and error shortcut. Once the blocker is resolved, reopen that menu and choose **Retry switching this conversation to …**. If a retained request is holding the switch, choose **Review retained requests** to see its delivery state and available actions before retrying the switch. If those records are unavailable, **Refresh recovery choices** checks them again and keeps the selected destination. If an unfinished goal holds the switch, choose **Open goal recovery** to inspect the goal or open the selected project in an independent conversation while the goal stays in its original project. When the same delegated task starts while recovery is open, the menu refreshes on your next choice. It shows the current state and lets you inspect the linked work. If that work becomes unreadable, the same recovery menu keeps the original details and destination and offers **Refresh recovery choices**. You can also open the destination in an independent conversation.

When your conversation needs setup, the editor shows **Setup needed**. Write your request and press the displayed submit key to choose **Open setup** or **Return to request**. If the only missing prerequisite is a project execution runtime, choose **Configure execution runtime**. This also works when you return to the same project conversation after an earlier response. **Save and apply runtime** returns directly to your draft in the same terminal. The runtime save review shows whether a metadata check found the Docker connection and image for the selected route. Choose **Check connection and image first** to run the optional check before saving. This check observes metadata. The first project request still checks its actual execution environment. The request stays in the editor exactly as written. When setup clears the displayed blockers, the editor shows which key sends the preserved request. Existing work, goals and retained sent requests continue to use their original recovery controls. If this conversation needs its original external model profile, open setup and select the first recommendation for a command that reopens the same app home and conversation. Replace the example profile path with your original private file.

Once setup is complete, `/ready` offers **Choose how to give your request** in a project conversation. If you already wrote a draft, choose **Return to draft**. The same choice shows the current key for sending it separately from the editor. If the editor is empty, choose **Return to conversation · write a prompt**. Choose **Managed task · review a request before starting** to open the explicit task form. In a conversation without a project, **Return to your draft** goes straight to the editor. **How prompts and managed tasks work** explains both routes. Choosing a method sends no request; a prompt is sent from the conversation, and a managed task starts only after its separate review and confirmation. Existing work, goals and retained requests keep their own next-step recovery paths.

`/ready` opens a short overview of the next action and current project, model, account and relevant runtime. When a goal owns the next step, open it to see what you can do, including configuring the execution environment when the goal can run. For an ordinary owner conversation, the next action follows a request that is preparing, waiting to start, responding or cleaning up. Choose that row to return to its conversation. If a single queued request has a recorded failure, the next step opens that exact request and its diagnostic. Other retained requests can be reviewed through the request list. Your current draft stays in the editor during either review. If you select the conversation’s first model during request review, gitjig returns to the original request when it is still current. Choose Retry separately to send it. A held managed task remains available through its original work and recovery options. If the current assessment is unavailable, open the original work and choose **View result** to read the recorded diagnostic. Cancellation remains a separate review of that same work. Use **Active runtime** for separate environment setup. A saved bridge change can require a restart to take effect. With a configured direct model, you can apply the runtime and proceed in the current session while that bridge change is pending. Open **More settings and details** for future model defaults, saved runtime and startup settings, bridge details, language and local/repository tools. If **Active runtime** is not configured, the row can open runtime preparation or review of the pending saved runtime directly. Select a configured **Active runtime** to open the runtime editor. **Inspect current runtime** shows the active profile. Checks and edits in the editor use the staged settings, which can differ from the current route until you choose **Save and apply runtime**. **Back to current setup** returns to the overview; **Return to request** closes it. These navigation choices keep the request and do not start work. Repairs and restart instructions remain visible in the current overview when needed. If your current model and any required active runtime are available, a saved startup warning appears separately from your next action.

The row above the editor shows request preparation, queued input, response activity and cleanup, with elapsed time during work. For a project request, the time carries through checking the project folder, model, and request or file references. If setup is needed, the draft returns to the editor for you to send separately. When space is tight, the heading and activity row may use shorter wording for the same stage, such as **Request queued** or **In execution queue**. The stage and available Esc shortcut take priority over the optional time since the last output. After an interruption or cancellation finishes, the activity row points to /inputs if requests remain for review. Reopening the conversation still shows the interruption when gitjig can verify the current settled run and its original retained request. On terminals that report held-key repeats, press the confirmation key separately for each review step. Held direction keys still move through choices. During a live response, an additional input shows its own preparation stage. After the request is received, Escape requests a stop while gitjig finishes checking what happened to the send. The terminal confirms retention for a still-queued request or points to the conversation and /inputs to check delivery. If the shortcut says **Esc cancels this send**, Escape cancels the additional input’s preparation and the original response can continue. Before admission, look for **Checking selected model** or **Checking request and file references**. Escape cancels the current preparation. After a pre-receipt cancellation settles, the conversation shows a short preview under **Not received**, including after restart. The editor shows the current draft separately. The next accepted request removes the preview. If a suggestion list is open, the footer shows its configured close key first. Escape also cancels a suggestion lookup that is still loading. If you edit before a suggestion can be confirmed, the previous list cannot replace your new text. Press the submit key again to use the retained draft. When a legacy terminal combines a rapid Escape and Enter into Alt+Enter, use the displayed close key and press the submit key separately.

**Request received** confirms the input was saved. You may see this before gitjig starts the request. A delivery check appears for additional input when the live session can receive it. Once gitjig accepts the request, **Request received · waiting to start** means gitjig has accepted the input and has yet to put the run in the execution queue. **Waiting for execution capacity** means the run is in that queue. **Starting request** means capacity has been granted and local startup is underway. **Preparing execution environment** includes checks after the snapshot is read and before the environment is created. Open `/ready` to see the current preparation stage and return to the conversation. This also applies when you retry a specific request from /inputs. While the Esc hint is visible, you can stop that attempt and keep the queued request. You can draft the next message while the request is waiting for execution to start. Once execution starts, Enter queues additional input and Alt+Enter queues a follow-up. The shortcut changes when the queue is available. The live-input shortcut appears when the running session has received the original input. During cleanup and **Finalizing response**, either submit key keeps your next request for review through `/inputs`. It stays there until you review it, even if the previous response finishes while gitjig is checking the new input.

**Preparing request for model** covers local preparation after a session is allocated. **Waiting for model response** starts at the local dispatch commitment. Native output distinguishes thinking, response text, tool execution and retries. The conversation heading shows the same current response stage as the activity row. The conversation picker updates that stage while you browse, so you can see what another conversation is doing before switching. It can show a response in progress alongside a recovery warning about related conversations. In the conversation pane, you can still see your response result near the editor while the related conversation’s recovery warning remains visible. When you reopen a conversation, **Last response completed** identifies its recorded response. Your saved draft stays in the editor and the current send or recovery guidance stays available. Its search and relationship guidance use the current conversation’s interface language. Search by the stored name, project or conversation ID. Model stages have no default overall time limit. The response status changes when the provider starts a reasoning, text or tool-call block, even before a fragment arrives. A “No new output” duration starts when model dispatch or native output is observed. The overall elapsed time still includes local preparation. Silence does not prove that the provider is healthy or has failed. Hosted Claude Code sessions also show provider-reported retries and usage limits while they occur. A reported reset time is information from the provider, not confirmation that a request can resume. These notices clear on a new response or when the original execution settles; they do not change its retry policy or task standing.

Escape interrupts the current response. If you interrupt during startup after admission, the heading shows **Stopping request** while the original startup settles. Pending sent requests remain available through `/inputs`.

If an earlier retained request blocks a new draft, the editor shows the submit key that opens its review. If gitjig cannot read the retained requests, choose **Refresh retained requests** to check again or **Back** to return to your draft. The current draft and the earlier requests stay in place. The new draft stays in the editor while you review the earlier request. After withdrawing the last retained request, the terminal confirms the withdrawal and that the new draft remains unsent. Select a request to see its recorded delivery details and exact text. **Queued request · delivery needs attention** identifies the request with a recorded routing error. The pane points to /inputs for a recorded delivery issue after reopening. The review shows the recorded reason first and keeps a distinct earlier run diagnostic below the request. Escape returns to the list. Use **Next page of the original request** for a longer review, then **Open recovery actions** when an action is available. If local preparation failed before the session received the prompt, review the original and use the offered retry after correcting the reported cause. The retry uses the original request and spent attempts stay recorded. If the original work has used its execution allowance, open **Review original execution allowance** from that request. Leaving the allowance review returns to the same request and draft. Choose Retry separately after extending the allowance. For an affected older request, the review can identify an unused session reference. The offered retry or withdrawal clears that reference and keeps the original execution records.

A completed response is separate from task completion. After an unexpected process exit, **Delivery needs reconciliation** in `/inputs` means the original request has a native attempt or may have reached the session. Open the original work for its retained details. Closing the work menu returns to the same request or its list of blocking work while the request is current. Press Back from the blocking-work choices to read the request again. Back or Escape in the ordinary request action menu also returns to the same request details. The input stays held while delivery needs reconciliation. When the first request was recorded before model dispatch and gitjig can verify its original session entry, the conversation can show that request with a read-only preview label. Opening the preview leaves the delivery hold in place. When that first request also qualifies to continue, open `/inputs`, review the original request, and choose **Continue original request**. Continuing uses one attempt from the original work’s remaining allowance and keeps its previous session on record. It requires the original model and runtime and unchanged captured project contents. If the new attempt fails before model dispatch or its delivery becomes uncertain, the request stays held for inspection.

A newly delivered request with captured files shows your original text and a captured-file count in the conversation. Use `/session` for file reference and capture details. If you retried an original request, this view shows the file comparison for each retained attempt that it lists. Older entries can display the full saved model input.

To leave and keep an unsent request, press Ctrl+G then Q. Use your configured command key in place of Ctrl+G. Gitjig saves the draft and waits for owned work to settle before closing. Ctrl+D leaves only when the editor is empty. `/quit` is also available as a command.

Keep the canonical application home outside registered projects. In the UI, use `/project` or Ctrl+G then J to select a registered project or register a directory and ID. Selection applies to the current conversation and retains its history and draft. If the selected folder is unavailable, `/ready` guides you to restore it or select a project before starting request setup. Active work, pending input or an unfinished goal can prevent a scope change; registration remains saved if attachment is refused. Project selection does not grant execution or repository permissions. A child result can be complete while its resource cleanup is still uncertain. In that case, inspect the blocking work through `/error` or `/work`; project selection does not discard the wait or retry cleanup. Older accepted results can release their original wait once their recorded resources are settled, without rerunning the task. “Recorded completion needs reconciliation” means the original result wait is still unresolved; it does not mean a model is still producing the result.

The command-line alternative is:

```sh
gitjig project register --home /absolute/gitjig-home --id example --root /absolute/project
gitjig local inspect --home /absolute/gitjig-home --project example
```

Read-only local inspection does not require a model or engine. Rules and project protection remain readable when saved agent setup needs repair. Rule inspection reports the optional runtime as configured, unconfigured or unavailable, including whether it came from saved settings or a complete explicit override. Unavailable settings include repair guidance; a configured runtime still needs execution preflight. Invalid explicit runtime options are refused. Save execution setup once with `gitjig setup save --file /absolute/private/setup.json`; see [Application startup setup](startup.md). A complete invocation override requires an absolute trusted `--docker-binary`, an explicit `--docker-context`, and an immutable `--image sha256:…`. Optional `--docker-config-directory` selects its Docker configuration directory. The override replaces the whole saved runtime. The selected backend must enforce the required work/scratch mounts, protected paths, execution restrictions and cleanup. The separate Interactive runtime installer can prepare Colima and build the image; metadata editing and Save alone do not create an engine. See [execution images](runtime-image.md).

`doctor` reports missing prerequisites. It does not provision a daemon or certify restriction enforcement. Without an engine context, `doctor` checks application prerequisites. With `--docker-context NAME`, it also requires a reachable engine. Colima is one tested backend; Docker-compatible backends must satisfy the same execution restrictions. See [Capabilities and limits](capabilities.md).

When a command names a retained checkpoint, use its original operation and project. A local check continues through `local check` or `work resume`. A project investigation continues through `conversation start` with its original project and retained model route. The error identifies which checkpoint rule failed.

## Models and credentials

Gitjig stores application preferences, accounts and models in its own home. Stock Pi settings and credentials do not configure this application implicitly. Account and catalogue commands work without an execution engine or a model turn:

```sh
gitjig auth status
gitjig auth login --provider PROVIDER --method api_key
gitjig auth logout --provider PROVIDER
gitjig models list
gitjig models default --provider PROVIDER --model MODEL
gitjig models scope --patterns '["PROVIDER/MODEL"]'
gitjig models roles
gitjig models role-set --role reviewer --provider PROVIDER --model MODEL --thinking high
gitjig models role-reset --role reviewer
```

Login also accepts `--method oauth` where Pi offers it. Logout removes the application's stored credential; it does not claim upstream token revocation. Model discovery describes the catalogue, not provider entitlement. Use `models configure --file ABSOLUTE_PRIVATE_JSON_FILE` for admitted compatible endpoints and `settings inspect` to inspect effective preferences. UI equivalents include `/login`, `/logout`, `/accounts`, `/model`, `/model-default`, `/scoped-models`, `/thinking` and `/role-model`. Cancelled dialogs preserve the command draft. `/scoped-models` offers staged catalogue/pattern additions and indexed removals. Save applies the application cycling pool; Cancel keeps the old file. Pi patterns, wildcards and `:thinking` suffixes remain supported, and a direct JSON array is available for advanced use. An empty pool makes `/model-next` unavailable. Scope does not change current choices or model defaults.

`/settings` offers plain boolean, enumeration and numeric values. Model defaults open the paired model picker; `/settings modelThinkingLevels` stages per-model requested levels and reset operations. Entries for models no longer in the catalogue can still be removed. Reset removes the application entry. Project overrides are shown separately and can remain effective after an application save. A changed preference file or conversation during editing requires reopening the form. Explicit `/settings KEY JSON_VALUE` remains available for advanced values.

Role overrides apply to future role launches. An unset role inherits that work's captured model baseline. They do not change a dialogue's selected model, an existing work baseline or a running binding. A new `change start` without `--model-profile` captures the application default; a paired `--provider` and `--model` selects an explicit application baseline, with optional `--thinking`. Existing application work resumes using its retained baseline even if the global default changes. It rejects a conflicting `--model-profile`.

After a model context limit on application-managed work, the result can point directly to the role required for the next stage, such as `/role-model adjudicator`. Model choices show the catalogue's context window and maximum output in tokens. If the role has an override, choose **Use each work’s captured model** to remove it, including when the model catalogue is unavailable. The change affects future launches of that role across the application. Provider access and successful execution are verified at their own boundaries. Review the original work and its remaining allowance before resuming.

For a managed task with mixed verification duties, the accepted plan can distinguish behavioral cases, an original pre-edit baseline observation and complete file-scope evidence. The application runs the required base check before admitting an editing producer. A successful baseline harness demonstrates its declared subject defect; it does not mean the application was already correct. Scope comparison and required independent review remain separate. When a candidate violates its accepted file scope, open `/result` or `/change inspect WORK_ID` to see the original allowed paths, unchanged paths and evidence ID. Resume spends remaining allowance on a repair within that scope. If the accepted scope conflicts with the original request, review the evidence before resuming. When available, choose **Review file scope and replan** from the result or work recovery menu, or enter `/change replan WORK_ID`. Review the original request and the failed scopes before confirming. **Back without changes** is the default. The shell command `gitjig change replan --work WORK_ID` uses the original app home, runtime and model setup. Pass `--home` if the work uses a custom app home. The original failed scope is reconsidered independently on the same work. Replan uses the remaining allowance and preserves the request, checks and original evidence. After the plan is accepted, open `/result` and choose **Review how to resume this work**. Confirm the original task to run the remaining stages through current checks and independent review. Inspect the original check/evidence IDs and blockers when verification is unavailable. The result shows recorded unresolved findings alongside a later interruption when both are available. Open `/work` for the individual dispositions and recovery actions. Resume preserves the work, old failures and spent allowance; it cannot manufacture a missing historical baseline or replace required evidence with reviewer prose. A new typed plan keeps typed accounting on later replans. Mechanical nits currently use ordinary repair and fresh verification/review, so the original finite allowance may stop the work before the extra review; no silent extension or usage reset follows. The available original scope or failed-check replan also opens from the original `/work` recovery menu.

If required consumer checks passed but independent review found missing evidence, **Review missing verification and replan** can appear in `/result` and `/work`. Review the original finding and confirm to plan additional cases for the existing checker. If the plan is adopted, choose Resume to run the new checks and independent review on the retained candidate. The finding stays open until that new evidence is verified.

Plain `change prepare` remains model-free and requires an explicit profile when later driven. Add `--model-source application` to capture an application baseline during preparation. Existing work without an application baseline cannot silently acquire current defaults: supply its explicit profile. Project execution still needs saved setup or complete runtime operands.

Explicit external model profiles are owner-only JSON files outside registered projects. Preserve the existing credential store; do not put credentials in a project repository. The selected OpenAI OAuth form is:

```json
{
  "provider": "openai-codex",
  "modelId": "gpt-6.1-sol",
  "native": {
    "kind": "pi-oauth",
    "authPath": "/absolute/private/pi/auth.json"
  }
}
```

The profile reuses the specified existing Pi OAuth login. The profile and referenced credential file must be canonical owner-only regular files. Missing credentials refuse with a recovery message; there is no automatic model or account fallback.

Claude uses the explicit `claude-bridge/claude-opus-5-5` selection and `installed-claude-bridge` native profile. That profile also declares private startup directories and a pinned executable. Use [Startup setup](startup.md) for its directories, executable identity and fixed configuration. Merely installing a bridge does not grant project or repository authority.

See [provider integration](providers.md) for account modes and provider-specific limits.

## Conversations and managed changes

The UI entry is `conversation ui --home PATH`, optionally with an explicitly selected external `--model-profile FILE`, with optional `--conversation ID` or `--project ID`. Opening the UI requires no model or engine; executing project work requires the runtime setup described above. The source/npm launcher selects its owned temporary directory automatically. Source commands are:

```sh
node dist/cli/entry.js setup inspect --home /absolute/gitjig-home
node dist/cli/entry.js conversation ui --home /absolute/gitjig-home
```

The installed launcher supplies its bound home and artifacts directory automatically. The source home is selected by `--home`, then `GITJIG_HOME`, then `~/.gitjig`.

Without routing options, gitjig opens the last conversation you selected. If it was archived or deleted, gitjig opens the most recently used accessible conversation; if none exists, it creates one. Opening preserves its draft and model choice and does not resume work. The notice and retained status show this distinction. Use `/resume` or Ctrl+G C to choose another conversation, and `/new` to create one. `--conversation ID` selects an exact existing conversation; `--project ID` or an external `--model-profile FILE` without a conversation creates a new context. An existing external-model conversation can be inspected without its profile; execution requires the matching profile or deliberate model selection.

Use `/new` or Ctrl+G N to open an independent conversation. From a project conversation, choose Current project or Unbound control conversation; `/new project` and `/new root` select these directly. Without a current project, `/new` opens an unbound context and `/new project` asks you to select a project first. New conversations use the selected scope's saved model defaults. Their header shows the actual project/model before execution. Existing histories, drafts, work, goals and obligations remain with their original conversations. If existing work or a result wait holds a project change, open `/error` and choose the action that names your selected project, such as **Open my-app in an independent conversation**. To choose a different project, open `/new root` and then use `/project`. Opening an independent conversation does not acknowledge results, clear cleanup obligations, retry work or cancel it.

Use `/help` or Ctrl+G then `/` to search by command name or description in the current interface language. Command names and argument syntax stay the same in both languages. Enter runs the selected action through its normal dialogs; Close or Escape runs nothing. Arguments shown in the list describe the command syntax. Existing Ctrl+G letter navigation remains available. Menu-based discovery preserves your editor draft, including text that looks like a slash command.

If a slash command is unknown or has invalid syntax, your input stays in the editor. Use the suggested name or command syntax when shown, or open command search with Ctrl+G then `/`, using your configured command key. This leaves any earlier operation error available through `/error`. To send a request that starts with a literal slash, type `//` at the start.

If you cancel a slash command before it accepts the editor submission, the exact command remains in the draft. Press your submit key again to reopen it, or edit the draft to continue with something else. A cancellation can show a more specific outcome, such as discarding staged settings.

Use `conversation list` and `conversation inspect` to identify the intended conversation. The conversation picker selects a different conversation; the history picker selects a branch within the current conversation. An unrelated project conversation can require a different runtime profile.

The parent pane shows **Related work in progress** near the editor while an assigned child works in the background. When the parent is waiting for the child, its activity line distinguishes a decision on the plan, a proposal for an isolated fault control, and the substantive review. You can keep typing in the parent or open the child to see its current step. An explicit result wait shows what the parent is waiting for.

You can give requests in your preferred language. Agent progress, clarification questions and final replies use your conversation language; you can explicitly request another reply language. Agent working records, internal task reports and review results use English and retain the original request alongside its interpretation. English automatic continuations do not change your reply language. Use `/language ko`, `/language en` or another language tag to save this conversation’s reply-language default; `/language` opens its field and explains scope. The saved choice applies from the next model request and survives compaction and restart. `/language auto` returns to interpretation of retained human input. A new explicit request for one response can override the default without changing the saved setting. Context clone/fork copies the preference; unrelated conversations keep their own. Code, paths, quoted source and requested localized product content keep their intended text.

Supported interface copy follows a fixed Korean or English reply-language choice, including regional tags such as `ko-KR` and `en-GB`. In `auto`, the model interprets your human conversation while the interface uses the system locale captured at launch (`LC_ALL`, then `LC_MESSAGES`, then `LANG`, then the host locale). `C` and `POSIX` use English. Other reply/system languages fall back to English interface copy while keeping your reply-language preference. `/ready` and `/language` show the interface source. If your conversation is Korean but the system locale is English, use `/language ko` for Korean labels. No model call or character-based language guess selects UI copy. See [Capabilities](capabilities.md) for the current translation scope.

An assigned agent submits its English result with `conversation_report` and answers you separately in your conversation language. The coordinator reads the report, not your final reply. Missing or stale reports leave the assignment unavailable; they do not turn your reply into a successful internal result. History navigation, compaction and native Bash do not replace a completed task's report.

Use `/change`, or select Managed changes in `/ready`, to find retained work across all projects. You can filter to the current project, page to older/newer work, refresh, and open a scrollable detail view. List rows show the recorded phase; detail shows the current assessed state, next action, original request/model and consumed/reserved execution and resolution allowances. Selecting a work item does not run it or change the draft. `/change inspect WORK_ID` opens a known item directly. Escape from a catalogue item returns to its current project filter and page. Back out of a Resume or Cancel review to keep browsing that same page. Choose Start a new managed change, Resume a retained change or Cancel a retained change for an explicit action. `/change start REQUEST`, `/change resume WORK_ID` and `/change cancel WORK_ID` are direct forms. Resume and cancel can also find the work through the registry without an ID. If the conversation already holds managed work, open /result for that work. To start another change, open /new project and submit /change start there. The start review shows the exact registered project folder. After confirmation, the new start captures its current files. If the registered folder is unavailable or changed during review, restore the original folder or register and select the intended folder with /project, then review the start again. The active diagnostic also offers **Select or register a project** in /error. Synchronize that folder with the intended Git basis before starting if the prior change was delivered elsewhere.

When extending a shared work allowance in `/work`, an active work or unconfirmed cleanup in the shared lineage is shown before the amount and reason form opens. Once the work has settled, reopen the allowance action and check the available count. Available units exclude spent and reserved units. The resume menu shows both available counts in its request inspection option. Review the original and proposed counters and shared scope before confirming. The listed family members can be a partial preview; the displayed total and omitted count explain its limit. Cancel is the default for the final allowance-extension choice. Explicit confirmation changes only the selected allowance; it does not resume work or extend goal turns.

When you choose **Write a request** in Managed changes, closing the review or backing out of confirmation returns to your entered task intent. Press Esc in the task intent field to leave the form. Your conversation draft stays in the composer. If the project folder changes during review, the form keeps your request. Submit it again to review the current folder after restoring it if needed.

A conversation started with `/change start` can be found by the first line-sized preview of its original request. An earlier conversation request or a name you set remains the title.

After you confirm a managed start, the composer shows **Reading workflow rules**, followed by **Capturing project snapshot**, with one elapsed clock. The snapshot step uses the work’s execution allowance. When capture settles, follow the current task status or open `/work` for details.

When you review resume from a different conversation, the first prompt names the original conversation. Enter on Back keeps you where you are. Choose **Open original conversation and review resume** to move there and inspect its captured model, original request and remaining allowances. A separate confirmation starts the work. Both conversations keep their unsent drafts.

If the original conversation is archived, open its original work and choose **Review restore of original conversation**. Confirm **Restore and open original conversation**, then review Resume or Replan separately. Work from a permanently deleted conversation remains available for evidence inspection.

Use `/result` or Ctrl+G then R to read the current managed task's result. You can also choose **View result** in the original work menu. Closing that result returns to the original work menu. The retained-result catalogue shows the current project filter and offers project switching, page navigation and refresh in the conversation’s interface language. Back or Esc from the result actions, or cancelling a chosen action, takes you back to where you were reading in the result. Closing a catalogue result returns to the same page and project filter with that result selected while its row is still present. If the original work link cannot be read, the list asks you to choose a retained result. If a result cannot be read, the diagnostic identifies its work. Close it to return to the same view and continue browsing. The overview starts with the project, recorded check/review outcomes and any incomplete verification assessment. Owner scope changes and allowance extensions use explicit commands with recorded reasons. Closing an allowance form or leaving a workflow-rule review without adopting returns you to the same work in `/work`. Retrying or reopening does not reset consumed allowance or erase unresolved findings. Unknown external effects require reconciliation before another send.

## Local checks and repository rules

Use `/local` for selected-project Git status/history, plain convention fields, staged preparation, isolated checks, retained original-check continuation, candidate recording and historical commit audit, or the CLI entries in [Local development](local-development.md) to configure branch/commit-message conventions and prepare staged changes without an agent task. `local recommend` prints optional rules; `local configure` applies an explicit profile at the inspected revision. `local prepare` checks those rules and reports each outcome. It does not commit or substitute for tests and review.

Use `gitjig local git --home /absolute/gitjig-home --project example --git-binary /absolute/trusted/git` to inspect a registered Git worktree. The JSON result separates index and worktree status, retains rename origins and untracked/conflicting paths, and lists up to ten recent commits. Unborn and detached branches have explicit states. Register the exact canonical worktree root; linked worktrees are supported. This command works without a model, execution engine or valid saved startup setup.

Keep repository configuration stable and stop configuration-changing tools during inspection. This native Git entry is not an execution sandbox. Preflight refuses configured clean/process filters and partial-clone/promisor routes, but a concurrent configuration replacement can introduce a helper before a later drift refusal. That refusal does not prove that no helper ran or external action occurred. Use trusted Git directly for unsupported repositories. With stable configuration, inspection leaves the index, branch and work files unchanged. It issues no fetch, stage or commit command and does not approve a change. Submodule contents and ignored files are excluded; upstream names are local observations. Non-UTF-8 output, incomplete output, more than 1 MiB per command, commands exceeding five seconds, and observed drift refuse with recovery guidance. The observation is not an atomic snapshot; inspect again after further edits. A general commit/push gate remains unavailable.

`local check` runs a supported actor-neutral check with its explicit project/runtime inputs. It does not require an agent plan or review transcript.

Use `local evidence --project ID --work W --git-binary /absolute/trusted/git` to compare original successful /work command evidence with a fresh full source capture and staged raw blobs/modes. CURRENT is source/index correspondence, not test adequacy or commit authorization. STALE preserves the old result as history. Missing/uncertain/scratch-dependent evidence refuses. See [Local development](local-development.md#inspect-check-correspondence) for input scope, recovery and the remaining commit boundary.

Use [Repository inspection](repository-inspection.md) for model-free GitHub.com, Gitea and GitLab native observations. For native existing-setting updates and explicit protection creation, use [Gitea/GitLab configuration](repository-configuration.md). Those native profiles remain separate from the GitHub configuration paths below.

Use `/repo` (also linked from `/ready`) for target registration, explicit current branch-policy observations, staged common settings, retained-plan inspection and explicit preview/apply/audit/reconciliation through the existing journal. Credential prompts ask for a private file path, not token text. See [repository configuration](repository-configuration.md#use-the-terminal-interface).

## Entry errors and recovery

A home error identifies the affected path. `FOREIGN_HOME` means the nonempty directory has no recognized ownership marker, or its marker cannot be verified. Inspect its contents before changing anything. Do not invent a marker or delete existing files to bypass the check. To use a separate home, select a new dedicated directory:

```sh
gitjig conversation ui --home /absolute/empty-gitjig-home
```

`UNOWNED_STATE` identifies an unsafe type, owner, permissions or noncanonical directory. If a parent path is an alias, inspect the reported resolved path and use the canonical application home. A state or artifacts subdirectory is not a replacement application home. Leaf symlinks remain unsupported. `OWNER_BUSY` means a controller or unresolved ownership record still holds the home. Close the live controller; verify its producer has stopped before explicit maintenance. Do not delete a live owner's records.

For an ordinary send, the original text leaves the editor when the request is recorded. If the storage write fails during submission, the request stays in the editor and can be sent after storage is available. If delivery needs review after the request was recorded, use the error shortcut to open **Review original request**, or find the recorded request in `/inputs`. If the editor says **Draft unsaved**, keep the terminal open. Free space on the application’s storage if prompted. Use the displayed error shortcut and choose **Retry saving this draft**. A successful save keeps the text in the editor for a later explicit send.

In the UI, `/error` or Ctrl+G then E opens recovery choices for the last captured failure in the selected conversation. A short diagnostic appears above the choices. Choose **Error details** for a scrollable inspection that includes supplied recovery guidance and work/run IDs. Up/Down scroll and PageUp/PageDown page. Press Escape or choose **Return to recovery options** to go back to the choices. Press Escape again to return to the conversation. Inspection does not retry work, extend an allowance or change the draft. Ctrl+G E also works when a draft cannot be saved; a failed command alone does not mean the draft is unsaved. Reopening a conversation restores its current recorded response failure when the original request and attempt are still current. Other retained work remains available through its normal inspection commands after restart. Very large display fields are shortened explicitly.

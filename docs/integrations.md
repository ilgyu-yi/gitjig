# Register receivers and manage branch integrations

Audience: users registering local bare or supported GitHub branch receivers, or inspecting local/GitHub existing-ref integration records. The browser can explicitly send an unsent prepared original or reconcile an uncertain original through read requests. An unsent original also has a reviewed preparation action. Local and supported GitHub receiver registration have their own reviewed entries. Work starts through `/change`; explicit ordinary work delegation has its own target action. The target browser also provides reviewed first-operation preparation for existing owner work and its ordinary grant. A branch update does not close a hosted pull request.

## Register or inspect receiver targets

Open `/repo`, then **Integration targets**. This lists retained observations across projects without a model, runtime, credential or Git executable. Select a target, then **Inspect observed identity** to inspect its original project, endpoint, branch, pinned basis and literal path inventories. Historical observation is neither current permission nor a delegation. Unavailable records remain listed by original ID. Use **Older targets**, **Newer targets** and **Refresh target list** for navigation.

Choose **Register local bare receiver** for an existing dedicated bare repository outside the installation home and every registered project. Select its source project and enter the canonical receiver path, full existing branch ref, exact pinned basis object ID, publication inventory and authorized delta paths. The delta must be contained in the publication inventory. Each inventory has **Add literal path**, individual path **Edit/Remove**, and **Done** actions; paths are literal, without glob expansion. Read all review pages. The default confirmation is **Back without registering**.

Registration uses the configured trusted Git executable or requests its canonical absolute path for this attempt. It reads the receiver's identity, restricted configuration and pinned ancestry, and writes private controller client artifacts. It does not change receiver/source contents, create work or grants, consume a work allowance, prepare or send a change. It rechecks source/project correspondence and receiver identity before retaining the observation. Unsupported receiver configuration, changed scopes or missing ancestry refuse registration. Settings remain unchanged. Repeating registration creates a distinct target ID; it does not replace old targets or reset their work/grants.

For a disposable dedicated receiver, this example creates a bare copy without template hooks and removes the clone's remote configuration. Run it separately with your actual source and receiver paths:

```sh
git clone --bare --template= /absolute/source /absolute/receiver.git
git --git-dir=/absolute/receiver.git config --remove-section remote.origin
git --git-dir=/absolute/receiver.git rev-parse refs/heads/main
```

Use the resulting object ID as the pinned basis. Other receiver configuration must also satisfy the native restricted profile. Registration does not provision a receiver or certify ongoing authority.

Closing the application aborts and joins its native registration, including initialization. If cleanup cannot be confirmed, shutdown reports an error with the original registration client path after restoring the terminal. Preserve that path for recovery; do not assume retry removed its processes. That controller refuses further local registration; pure target reads remain available. Inspect the original client journal and resolve uncertain cleanup before starting another controller session. If the target committed before a cleanup failure, the diagnostic also names its retained target ID.

The hosted registration CLI also retains cleanup-unknown errors for the current controller. Further local or hosted registration is refused there; pure target reads remain available. Shutdown drains owned tasks and resources before reporting the original registration client path. If a target was committed or an exact concurrent registration was reused, its original target ID remains registered and is named in the error. Multiple failures retain all recovery paths. This hold is in-memory: keep the reported client journals and resolve uncertain cleanup before opening a fresh controller. Ordinary credential/trust refusals with confirmed cleanup do not create this hold. The hosted registration form below uses the same collector. Installed clean initialization shutdown has the scoped coverage below; installed fetch and cleanup-unknown shutdown remain separate.

Hosted registration binds the selected project's record and directory identity and the registered project-root set through native reads and commit. A source or scope change refuses the attempt; reopen registration with the intended current inputs. Existing exact-target observations preserve the original target ID and refuse changes to that retained identity. Per-attempt cancellation and Git configuration are available to trusted host integrations without changing application defaults. The terminal form below supplies these controls.

Pure CLI discovery and inspection bypass saved startup and producer recovery:

```sh
gitjig effect targets --home /absolute/gitjig-home --limit 25
gitjig effect targets --home /absolute/gitjig-home --before ORIGINAL_TARGET_ID
gitjig effect target-inspect --home /absolute/gitjig-home --target ORIGINAL_TARGET_ID
```

Target data is bounded to 128 KiB and pages to 100 records. Malformed, contradictory or oversized identities remain unavailable without repair. These entries inspect historical GitHub existing-ref targets too; hosted receiver registration uses the reviewed form below or its separate CLI entry. Work creation uses `/change start`; finite ordinary work delegation is available below. Reviewed first-operation preparation is available below. Registration alone does not complete the work or establish landing eligibility.

## Register a GitHub branch receiver

Open `/repo` → **Integration targets** → **Register GitHub branch receiver**. This entry supports an existing public personal-owner GitHub repository. Gitea, GitLab, private repositories, organizations and Bots are outside this normal integration profile; their repository-governance capabilities have separate scopes.

Select a registered repository identity and source project. If no identity exists, use `/repo` → **Register repository**, then return. The displayed conversation project is only a form default; registration does not attach or move the conversation. Set the full existing branch ref, exact pinned commit, publication inventory and authorized delta paths. Paths are literal, and authorized paths must be within the publication inventory. Invalid fields remain staged for correction.

Read all review pages, including the registered account and native repository IDs. The default is **Back without registering**. Explicitly choose **Register this observed GitHub receiver**. Supply a trusted Git executable when one is not configured, then a canonical private credential JSON file outside registered projects containing only a `token` field. These inputs apply to this attempt; cancellation writes no settings or registration. The native reader verifies that this credential is the registered personal owner of the public repository and reads the pinned ancestry.

Registration records an observed receiver and creates no work, grant, preparation or send. Exact repeated registration reobserves the original target ID; changed immutable scope refuses replacement. If a late navigation or cleanup error follows commit, retain the named original target ID and client path. Do not interpret that error as a rollback. Installed clean initialization shutdown has scoped coverage; installed fetch/cleanup-unknown shutdown and live GitHub authority remain unqualified.

## Delegate ordinary integration to existing owner work

Start managed work with `/change start` in its intended project. Work execution still requires its configured runtime and selected model. Then open `/repo` → **Integration targets**, select the receiver, and choose **Delegate ordinary integration to owner work**. This delegation form itself needs no model, runtime, Git executable or credential. It lists that target project's retained governed work and roots holding an existing grant for the exact target, including unbound ordinary-conversation roots and held entries with their reasons. No work appears until one exists; opening the list does not create or resume work.

Select an independent work root created by this owner. For a new grant, enter a finite limit from 1 to 100. Read all review pages, including the original request, source/work/target IDs, work epoch and scope. The default is **Back without delegation**. Confirm **Delegate ordinary integration to this work** to record the decision. This is an ordinary conditional integration ceiling for that work only; it grants neither descendant authority nor an approval override. Actual account permissions and current procedures still gate preparation and sending. The limit counts distinct integration operations, separately from the work's execution and resolution allowances.

A compatible existing grant shows its original scope, operation count and remaining count. **Keep this original grant** preserves its ID and all limits; it does not extend or reset them. Existing lineage grants keep their original scope. Context or inherited work cannot create a grant that shadows its original owner root. Cancelled, interrupted, unknown, busy or pending-activation work, unsettled cleanup/reservations, stale grant epochs and unavailable provenance are held. Recover the named original condition separately. Keeping or redeclaring a grant cannot renew it or increase its limit. Cancelling and explicitly resuming the same work can leave its grant stale. Use the separate recovery steps below. Retained preparation refuses stale grant authority before changing its previous evidence. Keep the original work, grant, operations and usage; replacing them is not a supported workaround. Preview supports up to 1 MiB of work metadata, a 32 KiB original request, 64 KiB per origin/grant/run record, and 128 runs with 1 MiB total run data. Missing, contradictory or larger records remain held without repair.

The decision adds only the original owner-grant source and grant records. It preserves the work, captured startup activation profile, operation history and spent allowances. It does not prepare or send. If navigation changes after acceptance, retain the named original grant/work/target; reopening their facts is a read. Use the separate first-preparation action below after the original work has its required procedure evidence. Existing unsent operations retain their original preparation action.

## Renew authority after original work recovery

First explicitly recover the original cancelled or interrupted work. In `/repo` → **Integration targets**, select the original receiver, choose **Delegate ordinary integration to owner work**, and select the held original. Read the hold, then choose **Review renewal of this original grant** when offered. Enter an owner reason, review the exact original grant/work/target and usage, then confirm **Renew this original grant**. The default is **Back without renewal**. This supports existing ordinary work or delegation-lineage grants on independent owner roots. An ordinary-conversation root must retain its original owner input and an idle conversation with no pending input or unfinished goal. Its existing lineage ceiling can target another project, including from an unbound root. The review shows root and receiver projects separately. This route cannot create a missing grant for an ordinary root or renew an approval override. Unsettled cleanup, producers, reservations or receiver transmission remain holds.

Renewal keeps the same grant ID, original issuer, scope, finite limit and cumulative operation count. It binds a new grant epoch to the current original work epoch and records your decision. It does not start a model, native request, preparation or send. Previously prepared operations retain their old captured grant epoch and remain ineligible until one of the reauthorization routes below. Renewal does not restore cancelled assignments, stale cloned contexts or old native execution identity. A current coordinator can use its remaining original ceiling only with current reviewed subject evidence and normal admission. The ordinary coordinator root itself is not a governed integration candidate.

For an existing definitely-unsent owner original, open `/repo` → **Retained integrations**, select it, and choose **Review original authority reauthorization**. Enter a separate owner reason, review the previous operation and current work/grant/candidate, and confirm **Reauthorize this unsent original**. The default is **Back without reauthorization**. Current successful procedure evidence is required; missing standing refuses before mutation. Native-origin, assigned or inherited authority, any send marker and historical transport observations cannot use this route. A definitely-unsent agent integration withdrawn by your cancellation uses the agent route instead: after renewal and recovery of the original task, the root coordinator's integration request for the same task and receiver reauthorizes the same operation and queues it on the normal agent integration path, which prepares and can send it. See [Usage](usage.md).

Reauthorization retains the operation/work/grant IDs, exact client identity, allowances and prior receipts. It archives the complete prior operation and clears its old live projection and authority. The result is **PREPARED**, not ready to send. Use **Review original integration preparation** to perform actual preparation, then review sending separately. Renewal and reauthorization do not refund or reset spent allowance. A stale review, cancellation or navigation before commit changes no authority; retain the named original if a later presentation error follows commit.

Renewal history is bounded to 64 events and 1 MiB of grant/source bytes, with 64 KiB grant data and 128 KiB per renewal event. Reasons are 1..4096 UTF-8 bytes. A reauthorization receipt must fit the original inspection limits: 256 receipts, 1 MiB per receipt and 2 MiB total. Larger or inconsistent histories remain held.

Owner recovery and reauthorization have installed local-Git coverage; ordinary admission restoration and separate lineage-ceiling renewal also have installed coverage. These observations preserve original identity and spent usage, but renewal alone does not establish governed completion or landing. Installed GitHub recovery and reauthorization of context-bound, approval-override or possible-handoff originals remain unqualified. Agent reauthorization of a definitely-unsent native-origin original has source checks only, with controlled procedure evidence; installed and actual-engine coverage are absent. Qualification uses scripted models and owned services, not live provider judgment or actual hosting/account authority. See [Capabilities and limits](capabilities.md) for the overall support boundary.

## Prepare the first integration for owner work

Open `/repo` → **Integration targets**, select the receiver, then **Prepare first integration for owner work**. Select existing independent owner work in that target's project. This action creates neither work nor authority; start through `/change start` and use the separate ordinary-delegation action when those prerequisites are absent. Selection and review are pure reads. Any existing operation for that work and target opens the original integration browser, including refused, confirmed or unavailable records. It does not allocate an alias to bypass recovery.

Read every review page: the original work/source/target/grant, candidate and procedure versions, remaining operation/execution/resolution allowances, holds and captured subject model. The default is **Back without preparation**. Explicitly choose **Prepare first integration for this work**. Trusted Git and any private hosted credential use the same per-attempt inputs as original preparation; cancellation changes no settings or original allowance. A captured work model remains bound to that work; legacy unbound work instead uses the displayed explicit invocation recipe.

The controller obtains genuine current procedure evidence before allocating an original. Missing standing refuses without creating an operation or charging a native attempt. Source, target, grant, candidate and model correspondence are rechecked after asynchronous preparation and inside original allocation. Uncertain or malformed transmission records hold the receiver/ref across works and retained registration aliases. Local overlap uses device/inode or canonical path; GitHub overlap uses repository ID, node ID or case-insensitive owner/repository path. The branch ref remains exact. Changed project, basis, inventory or owner policy does not make an overlapping endpoint independent. A valid preparation allocates one original using the existing finite grant, then uses the original native projection, candidate adoption and governed continuation. A derived candidate requires its own checks/review and may consume the work's execution and resolution allowances. Admission and later failure retain all spent allowance and name the original for recovery.

Preparation never sends. Inspect the returned original; `RESERVED` still requires a separate explicit send review and current eligibility. Closing aborts and joins owned preparation. Local and captured hosted native-client initialization receive the same cancellation signal and join their owned process groups. A fresh attempt that never constructs a client can settle without a nonexistent cleanup journal; existing clients retain their original reconciliation requirements. Captured authentication and original client identity remain required across initialization and cancellation. No projection or continuation may begin after close. Unconfirmed cleanup remains a recovery hold. First-preparation interaction coverage uses controlled procedure evidence; actual-engine procedure-to-preparation has separate installed owner coverage. Neither establishes live provider or hosting authority.

## Open the retained list

Open `/repo`, then **Retained integrations**. The list shows the original operation ID, target endpoint, branch and recorded phase. Details also identify the original project, work and target. It covers retained operations across projects, independently of the selected conversation project. Use **Older integrations**, **Newer integrations** or **Refresh retained list** to navigate.

Select an original, then **Inspect original integration facts**. This reads controller records only. No credential, model, execution engine, Git binary or accessible receiver is required. Inspection does not recover pending producers, allocate work, consume allowance or change authority. It preserves cancelled work and uncertain outcomes. Opening a record is not a request to resume its work.

The CLI provides the same bounded reads:

## Interpret recorded outcomes

- **Phase** is the original operation's recorded state.
- **Transport outcome** reports the retained native send result. An interrupted possible handoff remains uncertain.
- **Observed containment** reports whether a read observed the exact integration in the receiver history. It does not prove which send caused that history.

A confirmed branch update is not hosted PR closure, independent approval, current permission or software completion. Keep the operation, work and target IDs when investigating. The browser provides the reviewed original preparation, send and reconciliation actions below; inspection alone executes neither.

## Prepare an unsent original

For an original in `PREPARED`, `REFRESHED`, `REFUSED` or `RESERVED` without previous send intent or receipt, choose **Review original integration preparation**. Read every page describing its target, original grant and source, recorded candidate/plan/check versions, retained subject model binding (or explicit legacy recipe) and remaining execution/resolution allowance. Recorded phase is historical; the preparation action must still obtain actual current procedure evidence. The default is **Back without preparation**. Choose **Prepare this original integration** to proceed.

Preparation uses that original work and target. For work with a captured application or ordinary-subject binding, the focused conversation's model and current defaults cannot replace that binding. Unbound legacy work instead uses the explicitly supplied invocation recipe; its historical model identity is not verified. The review identifies which case applies. Use the configured trusted Git executable or enter its canonical absolute path for this attempt; GitHub also requests its private credential-file path. Existing initialized client identity is preserved, and settings remain unchanged.

The native projection can produce a derived candidate in the receiver's actual context. That candidate needs its own checks/review through the original workflow and retained binding or explicit legacy recipe, using the original finite allowances and applicable runtime prerequisites. Closing the host aborts and joins the whole preparation, including candidate capture and model-backed continuation. Missing procedures/runtime, changed source or authority, stale candidate, occupied original and exhausted allowance can refuse or retain incomplete preparation. Inspect that same original and restore its named prerequisites; do not replace work or reset spent allowance.

Preparation never sends the branch update. A `RESERVED` result permits a separate send review only if current original gates still pass. This screen prepares existing originals; first-time preparation, receiver registration and ordinary work delegation have separate target actions above.

## Send an unsent prepared original

For a `RESERVED` original without a previous send intent or receipt, choose **Review and send original prepared integration**. Read every review page: it identifies the original work, target and branch, exact base/head/integration commits, evidence, grant, owner lineage, allowance and holds. The default is **Back without sending**. Choose **Send this original prepared integration** only to request that exact conditional branch update. It can publish code and trigger receiver hooks or CI.

Use the configured trusted Git profile, or enter its canonical absolute executable path for this attempt. Settings remain unchanged. An initialized original client requires the same trusted executable identity; selecting another executable does not replace its marker. GitHub also requires the private credential-file path and current account/policy observation. Cancelling these inputs before admission leaves the original unchanged.

The existing sender still requires current procedure evidence, original delegation, source fit and native authority. Another original with uncertain or unavailable transmission on an overlapping receiver/ref holds sending and names both its operation and registered-target IDs. This is checked before native admission and again inside the final send-intent transaction. A hold discovered during preflight retains the charged attempt and receipts but creates no send intent. Read-only reconciliation remains available. Retained identities are classified through bounded controller reads. An uncertain original whose target is missing, oversized, malformed or contradictory conservatively holds sending when endpoint independence cannot be proved; inspect the named original rather than deleting or replacing it. Consistently identified publication and repository-configuration families are excluded. Distinct receiver/ref identities remain independent. Coordination preserves every registration, grant and spent allowance; it does not deduplicate registrations, pool operation limits, establish current native authority or serialize external writers. Native conditional updates still handle external races. Review does not grant eligibility. A changed source or reviewed operand during native preflight refuses before send intent. Stale review, occupied or quarantined work, cleanup holds and exhausted original allowance require their corresponding recovery. Read-only quarantine exceptions do not authorize sending. An admitted attempt consumes the original execution allowance even when preflight refuses. No new work, grant, allowance reset or replacement client is created.

After a possible handoff, inspect the retained outcome and use read reconciliation. This action never retries a previously attempted send. Closing the host aborts and joins its accepted native task; an accepted remote update can remain `UNKNOWN` until a separate read observes containment. Branch containment and transport certainty remain distinct.

## Reconcile an uncertain original

For an original in `UNKNOWN` or `INVOKING`, choose **Reconcile original integration · read only**. Review its exact target, base and integration commits, original work state, execution allowance and cleanup/capacity holds. The default is **Back without reconciliation**. Choose **Reconcile original receiver with read requests** to proceed.

The action uses the active trusted Git profile if configured. Otherwise, enter the canonical absolute path to a supported trusted Git executable when asked. This profile applies only to this read; it does not change settings or write-path configuration. GitHub additionally requires a private credential-file path. Local bare-repository reads require no credential. The original native client still checks executable trust/version and receiver identity. Invalid executable ownership/location/limits refuse before admission where available; native version or receiver failures may consume an admitted attempt.

A read creates private controller-owned Git artifacts and uses the original work's execution allowance and shared capacity. An admitted attempt is charged even if the read fails or is interrupted; an affirmatively never-admitted cancellation can release its reservation. No new work, grant, allowance reset or resend occurs. Healthy `ACTIVE` and `DELIVERED` work keeps its state and original client identity. Stale source, changed original facts and exhausted allowance refuse. Cancelled or interrupted work requires its separate original recovery path.

For exact GitHub write quarantine, an independent observation client can read only when the original run and its single retained quarantined allocation match and independent capacity is available. Observed containment does not settle that old cleanup or permit resume/resend. Additional unsettled runs, reservations or capacity holds still block the action. Local quarantine has no corresponding isolated route here.

A result stays attached to the original operation if you navigate away. Closing the view host or application aborts and joins the accepted read; it does not cancel the underlying development task. Successful read cleanup preserves its original healthy work state, including after restart. Unconfirmable new read cleanup remains held for recovery. Inspect phase, transport and containment separately after the result.

## Unavailable records and limits

An agent retry uses the original refused integration and its settled child, rather than creating a replacement. If the coordinator, owner direction, reviewed assignment, receiver or grant changes while evidence loads, inspect the original before retrying. Cancelled or still-running children and contradictory dependencies remain held. A refused retry preserves its previous evidence, source-fit receipts and usage. This path supports at most 64 reentries, 64 KiB of assignment/dependency data each and 1 MiB of retained operation data. It does not renew authority after cancellation.

Malformed, contradictory, unknown-family or oversized records remain visible as **Unavailable retained integration** with their original IDs. Inspection performs no repair. Consistently identified publication and repository-configuration operations belong to their separate browsers. Legacy local records with omitted family discriminators retain their supported historical identity checks.

Each page has at most 100 entries. Before inspection, operation data is bounded to 1 MiB, target data to 128 KiB, grant data to 64 KiB, and related receipts to 256 rows and 2 MiB total with at most 1 MiB per receipt. Historical grant ancestry is bounded to 64 works. Read-action context bounds original run history to 128 rows, 1 MiB total and 64 KiB per run; related capacity history is bounded to 128 rows. Exceeding a bound makes that original unavailable without deleting it. Large terminal detail is shortened with an explicit notice; the CLI returns full bounded detail.

Supported recovery preserves the original work, assignment, grant, operation and native client. Owner recovery and authenticated coordinator recovery have different provenance requirements; neither can turn a possible handoff into an unsent operation. Use the specific [recovery routes](usage.md#conversations-and-managed-changes) and [capability limits](capabilities.md) before retrying. Scripted model decisions and owned hosting fixtures do not establish live provider judgment or hosting authority.

## Restricted PR merge operator prerequisites

This profile needs a repository administrator as well as an authorized work owner. A successful local procedure, target registration or finite grant does not create the required hosting policy. The following walkthrough describes the existing manually coordinated owner path. The agent path uses the same native prerequisites; it has no tool that installs or temporarily suspends them.

Check these conditions before planning a merge:

| Area | Required state for this profile |
| --- | --- |
| Repository/account | Public, personal-owner GitHub repository; selected account/repository identities must match. This adapter requires actual merge authority **and** native `viewerCanAdminister: true`, complete policy visibility, and positively absent matching classic branch protection (`directRuleId: null`, no matched classic rule IDs). A non-admin account or a base protected by matching classic rules is unavailable here even if native merge permission exists. Organization/inherited or unavailable policy is outside this profile. |
| Destination | One literal existing base branch, for example `main`, and an unmerged same-repository PR whose source receiver and recorded confirmed publication identify its exact head/tree. |
| Base rules | Active repository branch rules with the merge account unable to bypass. Require at least one named status check and native strict up-to-date enforcement. Retain required check app identities when configured. Actual current-head distinct non-author account approvals must meet the native count. gitjig role reviews do not supply those approvals. |
| Other protections | Required code-owner review, last-push approval, review-thread resolution, merge queues and unsupported/inherited rule semantics are not implemented by this ordinary profile. Do not remove required project protections merely to make the profile eligible. |
| Procedure/authority | Current checks and independent procedure review for the candidate, a confirmed original branch publication, a separate finite ordinary merge grant and enough remaining original execution allowance for preparation, Send and reconciliation. |
| Destination restriction | A separate active repository ruleset covers **all branches except the literal base**. It restricts both branch creation and updates, and the merge account has no bypass. This ruleset must not apply to the authorized base. |

For `main`, the last row has this exact native shape. The empty bypass list is a sufficient example; gitjig checks the current merge account's observed inability to bypass. There are no additional excluded branch names or wildcard substitutions:

```json
{
  "name": "Restrict merge destinations except main",
  "target": "branch",
  "enforcement": "active",
  "bypass_actors": [],
  "conditions": {
    "ref_name": {"include": ["~ALL"], "exclude": ["refs/heads/main"]}
  },
  "rules": [
    {"type": "creation"},
    {"type": "update", "parameters": {"update_allows_fetch_and_merge": false}}
  ]
}
```

An authorized administrator can create or edit a branch ruleset in GitHub **Settings → Rules → Rulesets**, selecting all branches, excluding only `main`, and enabling creation/update restrictions with no merge-account bypass. Verify the saved native fields against the example, including the update parameter; a ruleset name alone proves nothing. The REST shape above belongs to GitHub's repository-ruleset API, not `gitjig repo configure`. See GitHub's [ruleset creation instructions](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository) and [repository rules API](https://docs.github.com/en/rest/repos/rules?apiVersion=2026-03-10). This guide performs no policy update and grants no administration permission.

Use separate publication and merge phases:

1. Agree the repository policy and administrator handoff before execution. Finish the original work's planning, checks and independent review. Publish its reviewed head to the registered source receiver through the existing separately authorized branch integration path. Inspect that original operation for `CONFIRMED`; retain its ID, head and tree. Stop at this endpoint while the administrator performs the next step. Do not ask a coordinator to run straight through publication and merge while policy readiness depends on an unspecified future intervention.
2. The administrator separately reviews and activates the destination restriction. It must be effective before merge preparation and remain effective through dispatch. Read back its literal scope, active enforcement and bypass facts. Keep the base's strict checks and approval requirements effective. If policy already prevents source publication, stop and ask the administrator to decide whether a separately authorized policy transition is acceptable. Repeated publishing or an unreviewed bypass is not recovery.
3. Open the existing PR target in `/repo` → **PR merge targets**. If needed, separately delegate a finite ordinary merge ceiling to the original independent owner governed work. Choose **Prepare first PR merge** with that work and its confirmed original publication, review, then supply private credentials. Preparation rechecks current native and procedure eligibility; its preview does not. It sends no merge.
4. Open the retained original in **Retained PR merges**, review and explicitly Send. Inspect its returned outcome. Use the separate GET reconciliation action for possible handoff or readback; never resend to resolve uncertainty. For a definitely-unsent original, a restarted credential session needs preparation of that same original again. An UNKNOWN original remains GET-only. Each admitted preparation, Send or read can consume another execution allowance.
5. Before the next source-branch publication, account for the still-active restriction. It also blocks creation and updates of source branches for an account without bypass; completion of this merge does not lift it. Any later policy transition requires another administrator decision and native verification. Using native Git, synchronize the original project with the confirmed merged base while preserving local changes. For the new basis, use a fresh source branch, registered source target and new PR; the previous target's pinned basis is immutable. Run fresh checks/review and publish the new candidate, then have the administrator restore the required fence before its merge. Previous acceptance is not transferable, and Gitjig does not perform these administrator or source-synchronization steps automatically. A confirmed record in **Retained PR merges** offers **Before another hosted change** with this sequence.

Strict up-to-date enforcement also means that a concurrent base change can require a source update and another CI run. That update is held by the same restriction until the administrator resolves the policy sequence. Repreparation of an existing original can refresh a base only when it remains an ancestor of the unchanged published head. A changed head, uncertain send or unavailable policy must keep its original records and reported hold; this guide does not supply a general changed-head replacement or automatic policy-repair route. GitHub describes the extra builds associated with strict checks in [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).

The recurring administrator handoff and source-publication hold are material operating costs. This is a narrow coordinated profile, not evidence of low-effort unattended repeat use. Live repository operation, human waiting time, actual account rights and service enforcement remain unqualified. Keep those limits explicit when deciding whether to adopt this path.

## Retained ordinary PR merges

Use `/repo` → **Retained PR merges** to find an original existing-PR merge. Opening its recorded outcome makes no network request and grants no permission to send. Each action has a separate exact review and defaults to Back. Reviews show original work/source and target IDs, execution allowance, receipt limits and any producer or cleanup holds. Procedure and native standing are marked **NOT RECHECKED** until an explicit action performs those checks.

For a definitely-unsent original, choose **Review original merge preparation**, then **Prepare this same original PR merge** and provide a canonical private owner-only credential JSON file outside registered projects. This rechecks the same published candidate and current procedure/native eligibility, appending preparation receipts without allocating a replacement or resetting grant usage. It may refresh the native base only when that base is an ancestor of the unchanged published head; the retained result shows previous and current base. Preparation never sends.

Then reopen the original and choose **Review original merge send**. **Send this prepared original PR merge** uses the session that prepared it, without asking for another credential file. A restarted app or replaced credential session requires explicit preparation of the same original again. Current native checks, policy and the separate finite merge grant still apply. Inspect the actual returned phase; successful form settlement alone is not confirmation. These actions can each consume one remaining execution allowance.

For a possible handoff or confirmed original, choose **Review original merge reconciliation** and explicitly **Read this original PR merge**, providing fresh private credentials for GET requests. This spends one execution allowance while preserving original work, epochs and grant, including cancelled work or a stale/exhausted merge grant. It does not restore permission to send. A matching merged resource alone leaves a lost-response original UNKNOWN. A retained successful native response plus exact PR/tree/ordered-parents readback is required for CONFIRMED. Receipt limits can still prevent storing a large response. Close and interruption retain the original and settle the read; never send again to resolve uncertainty.

This remains the restricted public personal-owner GitHub same-repository profile in [Capabilities and limits](capabilities.md). Current native and procedure checks still govern each action. Owned-endpoint verification does not establish live account rights, provider judgment or general hosted merge support.


After explicitly recovering a cancelled or interrupted original owner governed work, use **Review original merge grant renewal** on its retained merge. For a grant with no merge original yet, select the held work under the target’s delegation action and choose **Review renewal of this original PR merge grant**. Enter a reason, review the exact original work/target/grant and cumulative usage, then explicitly renew. The default is **Back without renewal**. Only an existing ordinary work-only grant on an independent owner governed root is eligible. The same grant ID, issuer, finite ceiling and used operation count survive; advancing its epoch does not update existing operations or restore agent/context authority. Unsettled cleanup, producers, reservations and uncertain native transmission remain holds.

Then select the retained definitely-unsent owner merge and choose **Review original merge reauthorization**. Enter a separate reason and review its unchanged originally captured candidate, published head/tree, owner source and renewed grant. **Reauthorize this unsent original PR merge** requires current successful procedure evidence and archives the previous operation. The default is **Back without reauthorization**. Original operation/work/grant IDs, prior receipts and spent allowance remain; old native preparation and credential readiness are cleared. The result is **PREPARED**. Review preparation again with fresh credentials, then review Send separately. Neither authority action starts a model, native request or execution charge. Possible handoff never qualifies. Older originals without an initial bounded candidate snapshot remain unavailable for this new recovery route; no historical proof is synthesized from their current candidate row.

Reasons are 1..4096 UTF-8 bytes. Renewal chains are bounded to 64 events and 1 MiB total history; original reauthorization shares the existing 256 receipt, 1 MiB per receipt and 2 MiB aggregate bounds. Changed source/candidate/project/authority during review or evidence reads refuses without a new decision. A committed outcome remains discoverable under its original IDs after a later presentation error. Owned actual-procedure recovery and terminal mechanics are qualified separately from live-host/account support.

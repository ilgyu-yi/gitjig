# Capabilities and limits

Runtime setup includes an interactive existing-Docker/Colima helper and direct image building with bounded logs, elapsed time, cancellation and separate Save. Colima preparation paths cover macOS and Linux; the source terminal bootstrap can prepare missing Homebrew and Node/npm after review. Existing toolchains remain usable. This describes supported setup controls, not verification of every host/backend combination. Source tests use owned executable fixtures and real terminal input; build success alone does not qualify backend isolation or project tools. Optional extra Debian packages reduce manual image customization. An explicit selected-route check verifies engine/image presence, not isolation or complete project tools. Recoverable failures expose contextual setup/retry choices, and user-opened error recovery links to readiness or retained-request review. Cancelled, stale and unknown-cleanup outcomes keep their refusal boundaries. Existing profiles/settings are preserved, and local cancellation can leave package/VM/engine effects. See [Installation](installation.md) and [execution images](runtime-image.md).

Gitjig is in early development. The supported paths below have finite prerequisites and recovery limits. Repository adoption/contribution and overall workflow qualification remain incomplete. Unattended production use is not a supported deployment.

## Qualification scope

Selected source and installed workflows use the actual Pi SDK, isolated execution, checks, retained histories and native Git endpoints. Model decisions are scripted; hosting/account responses use owned HTTP/TLS fixtures. Some focused mechanics use controlled procedure standing. Their passes do not qualify a live model, account, service version or arbitrary combination of recovery paths.

Representative installed paths cover independent-owner and coordinator/child local delivery, the narrowly supported direct/inherited recovery routes, local developer checks/candidate/commit audit, provider-specific administrator guidance and the restricted PR merge sequence. Current native procedures and real checks remain required on their actual paths. A changed candidate or source invalidates affected evidence. Live provider judgment, service rights/enforcement and broader recovery combinations remain unqualified; this is not whole-product or dogfooding acceptance.

Managed verification retains paired executable cases for material behavioral guarantees. An explicitly accepted finite mixed plan can separately require an original frozen-base observation before any editing producer, and complete base/candidate scope evidence with an actual host-derived adverse input. These require exact typed witnesses and distinct independent review/adjudication; baseline observation is not a candidate passing check. This finite mixed profile is limited to original independent governed work; inherited/context-derived historical witness mapping remains unsupported. Legacy plans keep their original strict case rules. Missing historical baseline evidence after editing cannot be recreated retrospectively; unsupported qualitative strategies, partial manifests and stale or unavailable evidence remain blocked. A typed profile does not silently become legacy after replanning. Cross-plan historical baseline witness remapping remains unsupported in this first profile. Mechanical nits use ordinary repair, current checks/scope and fresh distinct review/adjudication; they can cost more resolution attempts than the legacy exact-nit carry and can stop at the existing finite limit. Original runtime/installed acceptance and provider qualification remain separate from model-free protocol and gate checks.

## Environment and execution

The source/npm route requires Node >=22.19.0 and targets macOS and Linux hosts; it has no CPU architecture allowlist. Official Pi 1.3.0 remains locked. macOS ARM64 with Colima Linux ARM64 is the current integrated test environment, not a product-wide platform restriction. Native Windows process ownership remains incomplete; WSL uses the Linux route. Prepared offline bundles currently include an exact macOS ARM64 runtime. See [Requirements](requirements.md) for dependencies and verification limits. See [Accounts and providers](providers.md) for provider-specific restrictions.

Restricted project execution requires an explicit backend and immutable runtime image. Opening the UI and managing accounts/settings do not require a model turn or execution engine. Gitjig does not provision the daemon, pull images or authenticate accounts merely because a conversation is opened.

A local source build is not a prepared installation. Use [Installation](installation.md) for the distinction. Health checks describe installation state; they do not establish model correctness, repository permissions or eligibility for another action.

## Results and authority

Models and semantic reviewers can make mistakes. A displayed input capture does not establish correct interpretation, and successful cleanup does not establish successful delivery. Inspect the attributed result and any pending findings.

Review-ready, completed goal, published summary and landed change are different outcomes. A failed, interrupted, waiting or uncertain operation is not completed work. Unknown external outcomes require reconciliation before another send. Native repository rules still apply, and successful agent procedures create no new account permissions.

Project capture includes dependency, ignored and untracked files within its entry/byte/time limits. Relative links inside a `node_modules` tree are preserved when their complete target graph stays in that same dependency tree and resolves to captured regular files or directories without cycles. Absolute, outward, dangling and other source links remain unavailable. Dependency links participate in capture and candidate identity; they do not enable symlink publication or staged-index correspondence.

English/Korean interface resources cover conversation chrome and response activity, command-menu navigation, shared picker controls, language selection, primary readiness/first-run and request-method guidance, project registration/selection, current-model selection, account-dialog controls and common runtime-field actions. The guided `/bridge` connection flow also uses these resources. Fixed `ko`/`en` reply choices select those labels per conversation; auto uses the system locale, and unsupported UI languages use English. Advanced repository/work/goal forms, some recovery/setup details, interactive provisioning output and upstream component hints retain English. Provider text, model output, protocol values, raw errors and retained evidence remain exact. Interface translation does not translate past replies or change English working records.

New governed assignment observations retain a compact result and an immutable original-detail reference. Detailed snapshots are limited to 16 MiB. The native coordinator can read that exact snapshot through `conversation_result` using the advertised `detailRead` operands and original result ID. Scope is rechecked on every page; missing or altered details remain unavailable. This differs from `/result` and `/work`, which inspect the selected current work. Existing large legacy cancelled assignments retain their bounded recovery limits; this does not renew task authority or change metadata allowances.

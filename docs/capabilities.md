# Capabilities and limits

Gitjig is in early development. The supported paths below have finite prerequisites and recovery limits. Repository adoption/contribution and overall workflow qualification remain incomplete. Unattended production use is not a supported deployment.

Choose a workflow below, then check its prerequisites and detailed limits before relying on it.

## Environment and execution

The source/npm route requires Node >=22.19.0 and targets macOS and Linux hosts; it has no CPU architecture allowlist. Official Pi 1.6.1 is locked. macOS ARM64 with Colima Linux ARM64 is the current integrated test environment, not a product-wide platform restriction. Native Windows process ownership remains incomplete; WSL uses the Linux route. Prepared offline bundles currently include an exact macOS ARM64 runtime. See [Requirements](requirements.md) for dependencies and verification limits. See [Accounts and providers](providers.md) for provider-specific restrictions.

Restricted project execution requires an explicit backend and immutable runtime image. Opening the UI and managing accounts/settings do not require a model turn or execution engine. Gitjig does not provision the daemon, pull images or authenticate accounts merely because a conversation is opened.

A local source build is not a prepared installation. Use [Installation](installation.md) for the distinction. Health checks describe installation state; they do not establish model correctness, repository permissions or eligibility for another action.

Runtime setup includes an interactive existing-Docker/Colima helper and direct image building with bounded logs, elapsed time, cancellation and separate Save. Colima preparation paths cover macOS and Linux; the source terminal bootstrap can prepare missing Homebrew and Node/npm after review. Existing toolchains remain usable. This describes supported setup controls, not verification of every host/backend combination. Source tests use owned executable fixtures and real terminal input; build success alone does not qualify backend isolation or project tools. Optional extra Debian packages reduce manual image customization. An explicit selected-route check verifies engine/image presence, not isolation or complete project tools. Recoverable failures expose contextual setup/retry choices, and user-opened error recovery links to readiness or retained-request review. Cancelled, stale and unknown-cleanup outcomes keep their refusal boundaries. Existing profiles/settings are preserved, and local cancellation can leave package/VM/engine effects. See [Installation](installation.md) and [execution images](runtime-image.md).

Project shell argument errors leave the current execution environment available for a corrected command. Bash timeouts are in seconds, up to one hour. An actual command timeout or uncertain execution failure still ends that environment. Git observations disable optional index refreshes by default; explicit metadata writes remain subject to the captured change scope.

## Results and authority

Models and semantic reviewers can make mistakes. A displayed input capture does not establish correct interpretation, and successful cleanup does not establish successful delivery. Inspect the attributed result and any pending findings.

Review-ready, completed goal, published summary and landed change are different outcomes. A failed, interrupted, waiting or uncertain operation is not completed work. Unknown external outcomes require reconciliation before another send. Native repository rules still apply, and successful agent procedures create no new account permissions.

### Project inputs and interface

Project capture includes dependency, ignored and untracked files within its entry/byte/time limits. Relative links inside a `node_modules` tree are preserved when their complete target graph stays in that same dependency tree and resolves to captured regular files or directories without cycles. Absolute, outward, dangling and other source links remain unavailable. Dependency links participate in capture and candidate identity; they do not enable symlink publication or staged-index correspondence.

English/Korean interface resources cover conversation chrome and response activity, manual summary/history progress and outcome labels, command-menu navigation, searchable command descriptions and slash-completion descriptions, shared picker controls, language selection, primary readiness/first-run and request-method guidance, project registration/selection, independent-conversation scope selection and recovery, retained-work discovery, evidence pages, allowance/cancellation/recovery reviews, current-model selection, account-dialog controls and common runtime-field actions. The guided `/bridge` connection flow also uses these resources. Fixed `ko`/`en` reply choices select those labels per conversation; auto uses the system locale, and unsupported UI languages use English. Advanced repository/goal forms, managed-change inspection and some recovery/setup details, interactive provisioning output and upstream component hints retain English. Provider text, model output, protocol values, raw errors and retained evidence remain exact. Interface translation does not translate past replies or change English working records.

### Retained results and cleanup

New governed assignment observations retain a compact result and an immutable original-detail reference. Detailed snapshots are limited to 16 MiB. The native coordinator can read that exact snapshot through `conversation_result` using the advertised `detailRead` operands and original result ID. Scope is rechecked on every page; missing or altered details remain unavailable. This differs from `/result` and `/work`, which inspect the selected current work. Existing large legacy cancelled assignments retain their bounded recovery limits; this does not renew task authority or change metadata allowances.

Final review retains the original findings, historical plan definitions, candidate and check/review evidence. Large histories can still exceed the selected model’s input capacity and hold the same work; a clear review alone does not close prior findings. Live final-stage capacity across large retained histories remains under qualification.

Managed implementation and independent review also assess cleanup caused by the change: obsolete/duplicate code, stale related documentation, unused dependencies and unintended generated or test artifacts. Cleanup follows functional edits and precedes final checks and independent review. Before removing or combining code or artifacts, assess affected references and consumers; a text search alone cannot establish nonuse. Intentional assets and required evidence remain protected. Concrete issues use the normal repair and review flow; cleanup edits need current affected verification and review. This is a review responsibility, not automatic deletion or a guarantee that every cleanup issue will be detected.

## Qualification scope

### Request limits and input capacity

An ordinary response can make up to 16 provider requests. Reaching that limit shows an application error with the original work inspection route; interruption remains separate. The sent request and work are retained, and no final assistant answer is implied. A matching current diagnostic survives reopening. Related assigned work is linked when its original receipt can be verified; incomplete link evidence is identified. Work execution and resolution allowances remain separate. For an original direct investigation, an already accepted parent wait can resume to inspect that exact settled failure. The child remains unavailable; this does not retry it or resolve its completion dependency. Pending owner direction, paused goals, exhausted allowance and uncertain cleanup can still hold continuation.

Governed change roles also have their own model-request count. New failures record when gitjig refuses the next request at that role's limit. English/Korean results and task summaries show the used count and route to the original work; coordinator results retain the same local fact. Existing work allowance, provider account usage and model context capacity keep their own controls. Historical failures without this fact retain their original diagnostic. Controlled SDK/Controller and separate source-installed checks exercise these views; live-provider qualification for this diagnostic remains pending.

Hosted Claude replies, governed role results and isolated summaries request up to 32,000 output tokens per response, or the selected model's smaller maximum. Enabled thinking shares that allowance. This is gitjig's response policy; it does not change the provider's intrinsic model capacity. Actual native compatibility remains specific to the selected executable and model.

Managed roles start with bounded source seeds and can discover additional captured files through native text reads. Discovery identifies the immutable version staged for that role; a file catalogue alone is not evidence of reading. Mandatory selected source text remains bounded to 1 MiB, assembled input to 2 MiB and each text read to 1 MiB, with the native tool’s separate rendering limits. Large mandatory source sets or individual files can still stop work. Source and public source/npm-installed qualification cover one 99-file project larger than 1 MiB, including actual EN/KO terminal request/start, off-seed consumer/checker reads, unchanged initial-input records and result reopening with its unsent draft. Model answers are synthetic over the actual installed HTTP codec and SDK. Managed role requests check the complete assembled SDK messages using local token estimates against the selected model’s declared context and reserve its full output allowance. These estimates are not exact provider token counts. Provider usage can reveal an underestimate and cause a later request to stop. Oversized requests stop before model dispatch rather than relying on a reduced response allowance. Initial optional source is capped at32KiB and can be omitted using captured managed-model limits before a role execution is allocated. Required inputs or later discovered context can still exceed capacity and stop work. EN/KO task summaries name a recorded model-budget refusal and link to the original result. Result and inspection views explain the cause while retaining the raw diagnostic; they do not retry work or reset its usage. Current cancellation and other recovery gates remain separate. Finite source and fresh installed EN/KO cases cover this budgeting at a declared128000-token context with16384 output tokens, including actual wire output allowance, off-seed discovery and retained result/draft reopening. A narrower100000/20000 source case separately verifies a context-limit hold with original charges and cleanup preserved. Broader project/model combinations and live model discovery remain under qualification. Capture or scripted success alone does not establish real provider acceptance.

Accumulated planning findings can also exceed model capacity even for a small project. Repeated claim text is shared without merging distinct findings or removing their pending obligations. Current adjudication supplies all current claim bodies and required criteria together; bounded history reads do not make that working set unbounded. For a work with no adopted plan or accepted-duty history, full old proposals can be read as needed while their exact intent and locators remain supplied. Current planning keeps historical requirement definitions, mappings, strategies and check guarantees inline, while selected old narrative and original-exposure lists use exact per-record read references. Adopted duties remain required; a needed unread detail requires reading the original or holding judgment. Older captured views retain their original delivery. This reduces initial history input but does not prove live model fit or evidence comprehension. Automatic partitioned adjudication is not supported. Repeating an unchanged request or extending execution allowance does not increase the model's context capacity.

Managed roles can use a declared operating view of product rules, with exact complete current and prior definitions available through owned reads. Large definitions may take several consecutive reads within the role’s existing limits. Core rules and changed or removed clauses stay supplied. An omitted rule or exception remains binding: a judgment that needs it must read it or pause. This reduces repeated input; it does not establish live model fit, comprehension or unlimited history. Existing records preserve their original delivery meaning.

Adjudicators receive a smaller core of planning and resolution contracts up front. Task-entry, verification, enforcement and historical-input rules remain available in full and must be read when the judgment depends on them. This preserves one final decision author; it does not add advisory model calls or make a previously oversized task automatically runnable.

Planning adjudication keeps current claim bodies and obligation states in its request; older decisions are available through a separate content-checked history read. That history artifact currently has a 1 MiB limit. Larger histories pause before another model request; earlier records and usage remain retained. This does not establish unlimited history or live-model completion.

### Managed response formats

A managed Claude role has a local limit on model steps. Returning a tool result to the same Claude query can use one of those steps. A submitted result still needs the original query to finish. If gitjig reaches its local limit first, the result stays provisional.

Claude planning submissions can correct ordinary role-validation errors within the current request. If the original submission stream is incomplete or conflicting when its message closes, that request stops; another submission cannot repair the earlier missing evidence. Original fragments, work and spent allowance remain recorded. Inspect the retained failure and use that work's available recovery action; existing findings, cleanup and allowance holds still apply. Process cleanup does not make the failed response valid, and this behavior does not establish live provider reliability.

Fresh Claude review adjudication uses one action per finding. The current literal review format can receive strict validation feedback and correct its submission within the same bounded request. Earlier formats retain their recorded carriers. Each received finding remains accountable, and the host independently checks the selected evidence after the result is returned. The correction path has controlled integration coverage. Live model adherence and latency remain unqualified.

The unreleased hosted planning integration candidate submits planner, challenger and planning-adjudicator results through a fixed validated tool. Validation feedback can allow correction within the same original bounded query; every received finding and spent request remains retained. A receipt means the result was received, not that its plan or judgment was accepted. Existing captured formatter and text histories retain their original readers. Controlled ordinary-default Controller planning covers submission feedback, independent rejected-material assessment, plan adoption and cold restoration; historical formatter/text routes retain their own controls. Private installed fixtures also cover this ordinary default without checkout module fallback. The judgments and execution boundaries in these controls are synthetic. Live retained work can reach recorded local review-ready, but that state alone does not independently establish verification quality or correct finding classification. Broader model/task/recovery qualification remains open.

The unreleased planning candidate supports an explicit remedy for a defect in the proposed plan. The original objection and pending remedy remain recorded until the corrected plan is actually adopted. Code-repair evidence and BASE implementation assignment cannot substitute for resolving the plan objection. Source and private installed controls cover adoption, failed adoption, source changes and cold restoration, including actual SDK submission feedback with a controlled producer. These controls use synthetic judgments and physical scopes; live model convergence of this remedy remains unqualified. A model can still misclassify a plan objection or a positive resolution narrative as an implementation defect, or miss a vacuous check assertion. These judgment errors can stop work or incorrectly support a readiness assessment; extending allowance alone does not correct them.

Fresh review adjudication explicitly states whether each upheld finding is pending, repaired or diagnosed. Passing checks and review evidence remain required for repair closure. This output guidance does not establish that a live provider will complete the requested format within its execution limit.

An initially accepted request can also exhaust context when the native structured-output formatter rejects a reply and the model attempts a correction. The rejected reply is not adopted. When the closed original execution provides an unambiguous formatter error, the result shows that earlier rejection separately from the final provider error. Incomplete or ambiguous evidence can still leave only the final error visible. Original role evidence and consumed usage remain retained; successful correction remains supported. Broader recovery remains under qualification.

Instructions to return JSON do not guarantee a valid managed-role result. Replies with narration remain unusable; code fences are accepted only by the explicitly declared review-response format described above. A bounded literal observation can be preserved separately with its original source and location while the reply remains stopped; incomplete coverage still blocks ordinary model execution. This does not qualify an alternative result channel or make a failed task complete.

### Retained failure recovery

Previously received findings remain obligations even when a later model response fails. Historical formatter-call reading can authenticate a completely received earlier call from its original retained checkpoint without treating the interrupted request as successful. Missing or conflicting original evidence still prevents reuse. This source-reading support alone does not establish successful task recovery. Explicit continuation can separately restore received-claim accounting for a settled aborted formatter whose only missing syntax is the final outer object delimiter, when all received role fields are closed, no findings member exists at any depth and exact original source/cleanup checks pass. The failed response, received claims, diagnostic and usage remain retained; other task gates still apply. Unknown, conflicting or more deeply interrupted material remains held.

A stopped tool submission can also retain an incomplete response. Supported bounded responses with intact original ownership and confirmed cleanup can continue through independent assessment of the exact received text and its recorded findings. The failed response stays failed; unavailable or ambiguous evidence still blocks continuation. Controlled SDK/Controller tests cover this recovery from source and a separate installation. Live provider reliability remains under qualification.

A stopped submission can also contain complete literal findings. Those findings stay available for later independent review when their original source can be authenticated; they do not need an extra incomplete-text assessment. The failed response and its used allowance remain recorded. Controlled SDK/Controller and private source-installed checks cover same-work planning continuation, including reopening retained state; live-provider and complete-task qualification remain pending.

Automatic repair stops when an unchanged candidate reproduces the same complete required-check failure. The result retains both failed runs and provides explicit same-work repair. A repeated file-scope violation stops automatic repair when the candidate remains unchanged. Explicit continuation can select a charged repair of that same work from matching current scope evidence, after any held owner input is assessed. Old failures and used allowance remain recorded. Controlled SDK/Controller and private source-installed checks cover this recovery, refusal when the evidence changes, and a real isolated check. Live-provider and complete-task qualification remain pending.

Rejecting a system-generated response-assessment duty requires independent assessment of the exact retained response and its recorded findings. Missing or changed original evidence cannot be cleared by changing the verdict. The original failed response and usage remain retained.

Explicitly resuming a supported retained response can run one independent assessment of the original text and its known findings. The bounded path requires the whole original response and intact histories under current settings and rules; unrelated evidence loss remains blocked. An assessment may identify more findings, which remain recorded for a later explicit continuation. It does not retry automatically or make the original malformed response valid. Completing this assessment alone does not finish the task. Broader response shapes and live provider reliability remain under qualification.

### Verification and delivery

Source result saving has source and installed coverage on finite local repository shapes. Preparation can take noticeable time as file inventories grow; broader performance remains under qualification. The [source save guide](integrations.md#save-a-result-to-a-new-branch) describes the available controls and refusal boundaries.

Normal replanning with a changed retained candidate requests source-qualified BASE classification. Initial planning and unchanged candidates retain the previous format. Selection is not repair evidence; the required source proof and independent judgment still apply. When a source-qualified plan binds a retained candidate and has no required before-edit check, resume runs current checks on that candidate. Fresh independent review and resolution still apply. If the shared execution allowance is exhausted, the retained plan shows how to extend it and resume the checks.

Managed verification retains paired executable cases for material behavioral guarantees. An explicitly accepted finite mixed plan can separately require an original frozen-base observation before any editing producer, and complete base/candidate scope evidence with an actual host-derived adverse input. These require exact typed witnesses and distinct independent review/adjudication; baseline observation is not a candidate passing check. A newly accepted BASE observation may explicitly name assertions expected to fail, while candidate verification still requires passing assertions. Older plans retain their original expectations; failure records cannot be upgraded after the fact. A check required before editing must use oracle files already present in the original base, or an explicitly declared inline oracle. Current planning rejects unavailable declared base oracles. A candidate check may use a new file if the declared change scope permits the additions it needs, including any parent directories it has to create. When a required check or review file conflicts with that scope, planning identifies the incompatible path and restriction before implementation. Use an existing suitable file or resolve the scope in planning. A retained missing-base-oracle hold requires independent replanning. This does not infer undeclared command dependencies or establish live model convergence. This finite mixed profile is limited to original independent governed work; inherited/context-derived historical witness mapping remains unsupported. One requirement can combine supported behavior, baseline and scope checks; every required part and involved independent reviewer must be available. Legacy plans keep their original strict case rules. Missing historical baseline evidence after editing cannot be recreated retrospectively; unsupported qualitative strategies, partial manifests and stale or unavailable evidence remain blocked. A typed profile does not silently become legacy after replanning. Cross-plan historical baseline witness remapping remains unsupported in this profile. Mechanical nits use ordinary repair, current checks/scope and fresh distinct review/adjudication; they can cost more resolution attempts than the legacy exact-nit carry and can stop at the existing finite limit. Original runtime/installed acceptance and provider qualification remain separate from model-free protocol and gate checks.

An independently approved plan can replace one consumer file in an isolated copy and run the same passing check against it. A faulty replacement must show the predicted failures. On newly started work, an approved conforming replacement must also pass with all declared observations unchanged. Both variants are optional and an accepted plan can select one. When the accepted plan assigns the replacement to an independent reviewer, gitjig requests the replacement after a passing candidate check. It runs the same check on the isolated replacement before starting substantive review. If the run completes with different results, review the observed differences in /work and use /change resume to request a fresh replacement for the same candidate.

Read-only local rule and protection inspection remains available when optional saved agent setup needs repair. Rule inspection distinguishes configured, unconfigured and unavailable runtime metadata and preserves valid saved or explicit settings without starting a bridge or engine. Common application ownership, project identity and invalid explicit operands still retain their refusal boundaries.

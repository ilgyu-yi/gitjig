# Design

## D1. Scope and architecture

The product has three capability levels, separated by responsibility rather than physical execution location (P6).

| Level | Responsibilities | Independently useful entry |
|---|---|---|
| Agent | Plan/challenge, implementation, independent review, procedure state, representative standing | Start or resume an authorized agent task |
| Local | Actor-neutral local development guidance and Git boundary checks | Inspect or check current local work |
| Repo | Configure/apply/audit repository rules, explain developer obligations, enforce change acceptance | Inspect rules or configure repository governance |

A review executed on the developer's machine remains agent-level when it orchestrates agent judgment. Repo-level need not interpret the internal agent review transcript.

Pi coding-agent is the primary agent runtime. Build agent integration around its public SDK, session, resource, event and UI facilities; local and repo capabilities remain independently usable. Select and exercise a supported Pi version explicitly rather than inheriting a legacy integration's API assumptions.

Each entry discovers available capabilities and applicable rules rather than assuming all three levels are installed. Agent-level may use existing Git/platform facilities directly when local/repo assistance is absent, but cannot ignore actual repository restrictions. Local-level assists human checks and review preparation without impersonating an agent task controller. Repo-level can configure and explain governance without a developer's local installation.

The integration seams exchange policy, check outcomes, and candidate identity. They do not require publication of internal agent transcripts or impose agent planning on human contributors.

Actor-neutral change inspection reads an existing registered worktree through bounded native Git commands. The effect adapter's owned bare client serves publication and conditional integration; it does not inspect or own the developer's index. Keep these responsibilities separate. Inspection reports exact local observations without advancing agent procedure state. Preflight refuses known helper or object-fetch requirements. Native local inspection requires stable repository configuration; it is not the agent execution sandbox. Post-read drift detection protects the result's validity, not against effects of concurrent configuration replacement. Avoid copying a developer's index, object database and Git configuration semantics merely to describe an ordinary trusted local view. Configurable working conventions and subsequent commit/check actions remain distinct boundaries.

The `/local` terminal surface connects the existing native observer and preparation functions to selected-project host forms. It stages finite plain convention fields and uses original revision/raw/root guards for Save, without a JSON requirement or a new rule engine. Each owned native read uses a bounded process group so cancellation or timeout cannot leave an inherited output pipe blocking shutdown; uncertain group cleanup remains explicit. Check execution, original-work recovery, source correspondence and native-commit audit are subsequent local boundaries rather than claims made by preparation.

Retained check details compose existing controller evidence inspection and candidate recording with source-bound forms. Record operations guard the reviewed work/result during evidence reads and immediately before exclusive receipt creation. Retained candidate selection carries a byte fingerprint and original-file guard across forms and asynchronous audit dispatch. Discovery does not initialize candidate storage. The terminal offers the historical audit after a separately performed native commit; it introduces no host commit executor or parallel evidence journal.

Local conventions use existing application-owned atomic configuration storage, with project/root identity, revision and exact-byte guards. Fixed literal fields express common branch and commit-message conventions without a rule language or an agent task. A preparation operation combines these preferences with the original native Git observer and captured message, returning attributable rule results. It does not install hooks, replace existing Git configuration or promote preparation into test/review evidence. Direct human commits retain native Git hooks, signing and update behavior. An optional precommit receipt binds the entire intended index tree, parent, message bytes, configured preferences and original check provenance in private application storage. A historical audit resolves a selected commit once, compares its immutable content with that receipt and keeps later work/policy separate. This avoids a second commit engine or interception of human Git. Governed agent actions retain their own action-boundary acceptance and authority requirements.

Source/index correspondence reuses the original command ledger and capture worker. Capture preserves relative links within one `node_modules` tree only after resolving their complete graph against the captured file/directory census, without following host aliases. Link text and topology participate in capture/effective identity and candidate deltas. Legacy link-free manifests retain their exact codec. External, absolute, dangling and cyclic links remain unavailable; native regular-file publication discloses excluded dependency links and refuses link changes. A controller-owned read takes a fresh full capture, validates the original command/result/manifest chain and compares each index blob/mode with private captured bytes. Git metadata and other captured context remain in scope; this is deliberately conservative rather than a dependency-impact heuristic. The existing native observer provides bounded full index and intent-to-add observations without writing a tree or invoking project filters intentionally. The original same-lineage recovery predicate governs unsettled-producer refusal. The inspection joins shutdown with existing owned preparations; it creates no parallel execution scheduler, command result or authority. Actual commit execution remains a distinct boundary.

## D2. Agent task path

The agent task controller owns transitions and evidence references; the author performs the work. Entry does not assume an issue or PR already exists. Stage-specific operations declare their prerequisites; authorized bootstrap creates missing objects before consumers run. Draft publication may occur when its own prerequisites are met, without claiming the change is review-complete. The normal path is:

`start -> clarify -> plan -> challenge/adjudicate -> implement -> verify -> independent review -> resolve findings -> action eligibility -> requested landing -> complete`

Planning/adjudication completes before implementation; C2 governs that boundary. C3/C4 govern review-ready delivery; C5 additionally governs external delegated actions. C9 defines endpoint completion. Implementation and finding resolution may repeat. Landing is optional under delegation; review-ready delivery is a legitimate endpoint. Interruption retains a resumable checkpoint. Unresolved requirements, unavailable required verification, or exhausted review resolution lead to a blocked state with a recovery request, not a fabricated success.

Owner-managed conversation work uses the same controller and governed path. A retained-origin resolver selects an existing governed original or establishes a new owner entry in the existing admission transaction. Ordinary source transitions share their family's allowances and intersect retained delegation ceilings. A controller-owned operation tracks the complete asynchronous path, including gaps between individual stages. Its private admission token permits its own work while public competing dispatch stays closed. This adds no separate scheduler or authority store. Closing the host joins this operation before releasing application resources. UI controls and actual endpoint acceptance must use this path rather than combine unowned calls to capture and drive.

Agent-authored progress, clarification and final replies to a human use that human's conversation language, following an explicit reply-language request when present. Agent working specifications, task normalization, internal coordination/results and canonical repository documents use English; normalization preserves the user's meaning and flags consequential ambiguity rather than changing requirements. Runtime instructions distinguish these audiences. An optional per-conversation language preference lives in existing controller state. The existing awaited Pi request hook refreshes a named language section without replacing native prompts or tools. Automatic mode keeps retained human references available; it does not guess a language code or require another model call. Generated English continuations do not replace the original human language context, and compaction retains reply-language preferences in its English summary. Original input, source quotations, code, paths, identifiers, protocol keys and requested localized product content remain exact. This policy does not require a language-detection service, extra translation turn or rewritten evidence.

An assigned ordinary dialogue has two result representations: the native final for the human and a separately captured English coordination report through the public Pi tool surface. The existing run/history and result journal own both provenance and publication; no second journal or translation model is added. New coordinator projections omit human reply text. Maintenance acts on native history without changing the original assignment outcome.

Application-owned interface copy uses typed message IDs and parameterized English/Korean catalogues. A fixed supported conversation reply language selects that pane's interface language. Automatic reply mode has no resolved language code: interface copy uses the captured system locale, with English fallback for unsupported languages. Expose that source without changing the saved reply preference or model language policy. Keep locales local to the conversation/pane and bind action dialogs to the source language revision. Choice values remain separate from translated labels, filtering and truncation. Never translate opaque user/provider text, paths, identifiers, commands or retained evidence through this catalogue. Support limits identify interface surfaces that still use English.

Apply ASD-STE100 writing rules and vocabulary to English documentation where practical. Define product terms and use each term consistently. State the actor, action and conditions. Separate long requirements into readable statements. A wording change must preserve obligations, exceptions and scope. Record necessary departures from the writing rules. Do not claim full compliance without verification. Apply this rule to new and revised text; historical evidence remains unchanged.

An operator can select any running subagent, enter its actual conversation, read retained history and live progress, and send instructions directly while the parent is working. The interaction targets the existing child session; changing the displayed/input destination does not replace or abort the parent or child runtime. Returning to the parent or another child changes only the view. Progress-only output and parent-model message relaying do not satisfy this path. Generic subprocess observation is a separate capability whose coverage may be narrower; it cannot substitute for interactive subagent conversations.

All conversation windows use the same ordinary conversation model. Root means that the conversation currently has no parent; coordinating several children is a role it may perform, not a special master-session type. A conversation may acquire children, or an existing conversation may gain a parent when work needs to be grouped. Relationship changes preserve its identity and history and do not implicitly copy context, change workspace/delegation, or reset governed-work obligations. A workspace/project is an execution target; parentage is a relationship between conversations.

Conversation switching is the default presentation, with optional side-by-side viewing. Each conversation retains its scroll position and unsent draft. Parent and child use the same input conventions. A compact activity/input-needed indicator and a shortcut-accessible conversation list expose related work; requests and completion update indicators without stealing focus or automatically moving the user. Each pane shows request preparation, queued admission, native response or tool activity, and settlement near its editor. Active states show elapsed time and the available response interruption control. A period without output is reported as silence, not proof of provider health or failure. Unknown state and input recovery remain distinct from active execution. Human navigation and agent-addressed commands use the same conversation identities and managed state. An agent can inspect and address conversations across authorized projects without changing the human's current view; command targets are explicit rather than inferred from that view.

Show actual parent-child relationships in the conversation selector. Open the selector at the current conversation and show its ancestor path. Keep search results in their relationship context. Each visible pane identifies its conversation and whether it receives input. Provide keyboard access to conversation selection, parent and child navigation, split controls and pane focus. Provide direct, single-chord navigation to the current conversation’s immediate parent and child without opening the command menu. For several children, return to the last selected accessible direct child, or ask the operator to choose. Recheck relationships before navigation; never substitute a different hierarchy level or an unrelated conversation. Native editing, search, completion and dialog input keep their own keys. These operations preserve conversation identity, drafts and scroll position. Show a pending summary operation and its actual outcome on the conversation that requested it. A completed request is not sufficient evidence of a successful summary.

Expand the footer for command selection while keeping the conversation and editor visible. Keep a bounded list with keyboard access to every command. Use the label Model for the active conversation’s actual native model, or its selected model before execution. An absent session alone does not mean a model change is pending. Read native model identity at render time so a change cannot leave a stale label. Keep the model visible in both footer states. Use distinct text colors for active input, context, command keys, model identity, attention and errors. Keep labels and dividers so that color is never the only cue. Keep the command toolbar visible when reporting a navigation boundary. Use a separate notice row that does not capture input. Clear informational notices on a human edit, a successful conversation switch or command-menu entry. Keep errors and summary outcomes attributed to their conversations. Each pane shows two bounded relationship rows: the immediate parent and accessible direct children with reported states and input-needed markers. Show an honest remaining count when children do not fit. Keep root and unavailable-parent states distinct. Use the existing selector for the full list.

Parentage is a coordination relationship: the parent can inspect progress, delegate work and consume results while each child retains its own context and execution state. Each child has one current coordinating parent; other conversations may reference its status/results. Reparenting notifies the old and new parent and preserves existing task instructions, results and waiting dependencies. A parent waits for a particular child result only when its task has that declared dependency. Within existing authorization, direct user instructions take precedence over parent-agent instructions. Relevant direction changes are reported to the coordinator; conflicting later instructions are surfaced rather than silently overwriting the changed direction.

Response interruption and work cancellation are distinct controls with visible scope. Response interruption acts on the current conversation response. Work cancellation covers the named work and the executions delegated for that work, using actual task provenance rather than the current visual conversation tree; unrelated connected work remains independent. Existing cancellation/reconciliation and cleanup obligations still apply.

A completed result remains an attributed observation when the same conversation receives follow-up work. Show delivered result and follow-up progress separately; publish a linked new result and notify the relevant parent when it is accepted rather than overwrite the result already consumed. Explanatory follow-up can preserve the existing result, while changed implementation or guarantees requires affected verification/review under the existing contracts.

## D3. Delegation and standing

A user supplies an explicit task delegation configuration. The controller evaluates actual account permissions, delegation limits, and procedural eligibility separately (P5).

Cancelled governed-assignment recovery preserves the task before recovering any external operation. A genuinely current coordinator under the same original owner root may explicitly restore one direct non-context assignment. Keep the original source, invocation and model binding; record a bounded current-authority event linked to the complete previous assignment. Launch, active lineage and queue admission resolve that event through one shared authority reader. Historical discovery continues to read original provenance. Restoration neither launches a producer nor restores cancelled dependencies or descendants. The original child must explicitly resume and establish current procedure standing. Later owner direction on the same root reaches the recovered task as exact held source input through the existing input subscription, with launch and the shared authority reader as the fail-closed fallback; it is never a coordinator-authored restatement. Old integration source tokens and grant epochs remain stale until their own separately authorized recovery; source-fit cannot manufacture a current native identity. Operation adoption that erases task provenance is not a recovery path. After task recovery, the same coordinator's existing integration tool can reauthorize the same definitely-unsent native-origin operation withdrawn by that owner cancellation: one transaction archives the previous operation, alias and dependency, rebuilds the operation as PREPARED with current tokens and requeues the same alias. It allocates nothing and does not itself send; the requeued alias follows the normal agent preparation and conditional send.

Direct ordinary clone/fork admission recovery keeps immutable context origins and continuations historical. A separate owner authority event bridges only the original direct edge after source-root recovery and bounded physical validation of both retained native histories. The shared live context reader resolves that event and includes its fingerprint in effect/publication tokens. Recovery changes only the same context admission epoch, without dispatch, grant renewal, input or allowance reset. Existing descendants retain their original stale epoch; new descendants can validate the recovered ancestor. Metadata inspection uses historical parsing without temporarily activating work, while physical reads share existing close-owned context preparations. This metadata route does not itself recover a cancelled inherited assignment or a family-source predecessor. A single cancelled outgoing inherited task may retain its exact cancelled wait as a bounded owner receipt: explicit public owner cancellation names the coordinator and actual epoch transition, and restoration withdraws only that scheduler wait. The original task and dependency remain cancelled. Its recovered current coordinator may separately restore that same task through the existing assignment tool, then explicitly reenter it. A pure bounded assignment-history reader separates original source provenance from current caller authority; the shared context reader validates the original native caller/input, archived wait, cancellation and direct-coordinator proof before resolving the inherited source epoch. It never rewrites ContextOrigin. Ongoing authority validation excludes mutable result payloads, while the initial cancelled snapshot remains fully bounded. Nested, multiple-wait, previously recovered/reentered and native-operation-bearing tasks require separate recovery.

The ordinary agent integration tool uses repeated source-bound admission around evidence loading and the original SQLite transaction. Retrying a refused original atomically replaces its evidence, consumes applicable source-fit proofs and requeues its existing alias/dependency. Validate the original grant epoch and settled alias correspondence first. A rejected retry cannot leave a partially refreshed original; it does not create a separate native-authority renewal protocol.

Original owner change entry records its normalized delegation profile before capture. A new independent ordinary owner root captures the same complete profile, including an empty one, and activates before reserving its initial run within the admission transaction. Existing ordinary roots keep their captured or legacy authority when startup defaults change; assigned, context, strict-review and predecessor transitions do not acquire a fresh profile. Activation commits publication grants, integration grants and completion together. A pending activation is a durable execution hold, recoverable on the same work after capture/cleanup settlement and an explicit epoch/profile check. A management-only activation retry does not recover or dispatch runtime work; completed activation preserves prior grants and usage. Context continuations keep the retained original authority source. A later explicit owner decision may add a finite ordinary integration grant to an existing independent owner work root. Record that decision separately; it does not rewrite the captured startup profile, renew a stale grant or reset work/operation allowances.

Stale integration-grant recovery requires two separate decisions: renew the same finite owner grant, then reauthorize and prepare any definitely-unsent original with current procedure evidence. Renewal history uses immutable owner source events linked through previous complete grant rows; shared admission verifies exact epoch transitions, unchanged operands, historical operation counts and original issuer correspondence. Bound the chain to 64 events and 1 MiB of grant/source bytes, with 64 KiB grant data and 128 KiB renewal-event data. Original source-fit cannot manufacture a renewed native identity after cancellation. Historical reads remain separate from action admission. The owner UI exposes these as separate reviewed, default-Back actions. Grant renewal covers existing ordinary work-scoped or delegation-lineage ceilings on independent owner roots. An ordinary-conversation root must retain its exact original owner input and idle conversation; its existing lineage ceiling may target another project, including from an unbound root. Bind authority to the receiver project and preserve the original scope. Only governed same-project work may declare a missing grant through this owner form. Definitely-unsent owner-original reauthorization remains a separate narrower route. Native-origin, assignment/context-bound or possible-handoff originals keep their existing recovery obligations. Reauthorization validates real current procedure evidence, archives the complete previous operation in a bounded receipt, and rebuilds live state from an explicit allowlist: original kind and client identity, current evidence and grant/root epochs, and PREPARED-only guidance. It clears live projection/commit/hosted-authority operands; explicit native preparation must establish RESERVED again. Neither owner decision creates work, resets usage, prepares or sends. New receipt count/bytes must fit the original inspection profile before commit; source/target/work/grant drift, evidence drift, cancellation and unavailable result correspondence roll back the transition.

Task execution permissions and representative action eligibility are distinct. Entry permits bounded investigation; successful planning permits implementation. Acting for the owner at a governed boundary requires the procedures applicable to that action, so the model does not require a finished review before work can begin.

Representative standing is scoped to the task, candidate revision, applicable rules, and requested action. The controller grants action eligibility only after required procedure evidence is valid. A merge request follows ordinary repository conditions unless a separately delegated override is required and actually available to the owner. No role name such as maintainer establishes authority. A repository that permits an owner to merge without another account's approval permits the corresponding agent path after procedure completion.

The registered-target browser composes owner work selection, late delegation and first integration preparation as separate explicit actions. First preparation reuses current evidence, original allocation, native projection and governed candidate adoption rather than introducing another workflow. Existing operation identity owns recovery. The reviewed pre-allocation snapshot transitions to that exact allocated original so its own candidate/allowance evolution does not falsely invalidate it; source, target, grant and subject-model correspondence remain guarded. Sending remains a separate boundary.

Hosted target registration accepts trusted per-attempt Git settings, cancellation and a synchronous host validator separately from the immutable receiver request. It owns credential-session exclusion before its first asynchronous project check. The original project row, canonical directory identity and project-root exclusion set remain bound through native reads and the final transaction, including observation of an existing target. This composes owner forms with the existing registrar without changing application defaults or adding a registration engine. Registration observes identity and ancestry; it grants no work or continuing action authority.

The hosted receiver form reuses the retained repository registry and normal public personal-owner GitHub registrar. Native repository/account IDs come from a selected observed identity, not numeric user fields. Visible staged project/ref/basis and literal inventories receive complete review and default-Back confirmation before per-attempt Git/private credential inputs. The repository command host leases credentials through registration and cleanup, supplies source and selected-identity validation to the original transaction, and retains any actually committed target ID before late navigation checks. Local and hosted forms share literal-path editing; neither changes conversation scope nor chains registration into delegation or work.

Receiver uncertainty coordination uses bounded read-time identity overlap across retained registrations. Local filesystem identity or canonical path and hosted native repository identity or normalized repository path identify potentially competing updates to the same exact ref. Unclassifiable uncertain records hold conservatively. Reuse the registry's consistent family classification and project only holding IDs/phase, rather than duplicate a mutable identity index, migrate registration authority or treat new IDs as independent receivers. The same query guards allocation and final send intent. Read recovery and each original grant's accounting remain independent.

## D4. Enforcement and evidence

The controller, rather than the author agent, maintains authoritative procedure state. Check runners and review executions return results to that controller. Evidence records the task, candidate, producer, outcome, and relevant inputs. An execution succeeds only when its result is complete, structurally valid, semantically interpretable, and bound to the intended run; process exit alone is insufficient.

The initial enforced agent profile uses controller-owned task state, an existing runtime execution restriction, execution-owned result writers, and finite typed action adapters. All author, reviewer, test and child execution stays within that restriction: declared work/scratch writes are allowed; controller writes and authenticated external mutation through direct clients or privileged relays are denied. Only supervisor-mediated tools are exposed in this profile. A shell hook alone is insufficient when another runtime tool can perform the same action. The supervisor dispatches fixed action schemas with action-specific prerequisites and targets; arbitrary shell, project helpers and nested actions are not privileged inputs. Project code never runs with dispatcher authority. Trusted adapters use installed control dependencies, clean environment and owned client configuration rather than project hooks, aliases, imports or credential helpers. Guards resolve the requested operation, consult current eligibility, and refuse unmet conditions before side effects. Resolve operation structure and effective target separately from quoted/heredoc payload data. Include hosting authority (host, repository, resource), effective filesystem paths, and action scope; exemptions apply only to their named obligation, not unrelated checks. Known equivalent operations through shell, Git, and hosting clients must share the same gate in a supported deployment; recognizing a preferred command alone is insufficient.

Existing runtime restrictions close alternative execution paths; agent-level hooks and command adapters provide early guidance and diagnostics. Declared dependency provisioning and owned nonprivileged fixture endpoints keep local development and verification usable without a blanket network or localhost exemption. Unsupported runtime/tool coverage is reported before activating enforced actions. Repo-level platform protections provide the repository's independent boundary. Controller state is outside the ordinary worktree and not supplied through agent-editable completion checkboxes. This targets skipped steps, opportunistic alternative commands, and stale results, not malicious host control or deliberate evidence forgery. No credential-isolation infrastructure is required solely by this draft. A deployment with uncovered alternative action paths must report partial/advisory coverage rather than claim complete enforcement.

## D5. Independent planning and review

Planning output uses contextual constraints captured once from its original input bundle. When that bundle contains an owner workflow-criteria refresh, schema guidance and final decoding bind the same source/from-version/to-version tuple. Require an independent criteria decision only on the accepting path that reaches adoption; an explicit refusal or owner-decision request does not need to manufacture adoption. Validate any supplied tuple in all branches. The host still checks the actual current refresh before acceptance. Final decoding occurs after the producer settles, so a protocol refusal preserves the original unusable output rather than implying an inline repair loop or another provider request.

The controller supplies each challenger or reviewer the agreed intent, relevant contracts, and candidate material in a separate execution context. Author, worker, and reviewer executions have explicit workspace/write ownership and preserve pre-existing user changes. Reviewers cannot mutate the author workspace; parallel runs receive independent scratch, fixtures, and environment. Before judging, the reviewer verifies the actual checked-out/effective content and comparison baseline; isolation alone does not establish that the intended implementation was reviewed. Author advocacy and other reviewers' conclusions are not default prerequisites. An adjudication role, separate from the author and the challenger whose claim is disputed, evaluates findings and alternatives against the same agreed criteria. The current independent planning adjudicator, distinct from the original finding producer, can explicitly carry each independently assessed initial-baseline implementation defect into the accepted remedy plan, preserving its pending finding and exact baseline/requirement provenance. This accounts for the planning decision while later changed-candidate checks and independent review establish actual repair; unresolved planning or source questions remain blockers. A user may make an authorized requirement or tradeoff decision; this does not turn an unresolved independent-review obligation into a pass.

The plan distinguishes user/product requirements from provisional solution choices and compares the simplest sufficient alternative, including reuse or no additional mechanism where appropriate. Challenge considers purpose, total cost, structural fit, and guarantees, not merely compliance with the planner's conditions. It may conclude that no better approach is justified; alternative generation is not a quota.

Separate runs, inputs, and result provenance establish procedural independence, not guaranteed cognitive independence or freedom from shared-model bias. The product records those limits and does not equate a fresh context with infallible judgment.

Review proceeds as finding production, evidence-based disposition, repair, and affected revalidation. Classifications do not collapse severity, validity, and repair type: a nit may be required but mechanically repairable; an optional preference is not a blocker. A non-author adjudicator resolves disputes and authorizes any mechanical carry-forward scope. A reviewer who proposes or authors a repair becomes an author of that repair and cannot independently approve it in the same resumed context.

A nit is eligible for carry-forward only when the exact remedy is fixed, leaves no design choice, and changes no behavior, contract meaning, or reviewed guarantee. The controller binds the reviewed before-state, exact authorized remedy and resulting whole delta, and checks relevant inventoried consumers; a checker or independent reviewer confirms it. Any extra change, failed check, or uncertain scope returns the candidate to affected review.

Keep raw received reviews alongside dispositions. Before any new panel, adjudication, or eligibility decision, the controller consumes pending diagnostic and recovery obligations. Each raw finding occurrence has a disposition or an explicit link to an equivalent finding; aggregation never silently drops minority or duplicate occurrences. Grouping a finding does not prove shared cause; a discriminating reproduction or checked source must support a shared remedy. A runner-observed material failure stays pending until the same bound input passes on the repair, a fixture/binding defect is demonstrated with a corrected invocation, or an authorized requirement revision changes that obligation. Unexecuted rebuttal prose or a different passing endpoint cannot discharge it.

Historical records remain immutable observations; one explicit current selection and supersession relation identifies the records used for this candidate. An incomplete transport result remains incomplete, but does not invalidate a later complete selected execution merely by existing. Superseding a review does not discharge its unresolved findings.

Track unresolved obligations across rounds rather than recreating an unrelated checklist each time. New findings must identify a real unmet existing obligation or obtain an authorized requirement change. Remove an unsupported nonessential claim when doing so preserves required meaning; do not grow explanation or test machinery merely to defend it. One adjudication function resolves review disputes; do not spawn recursive generative review-of-review layers. Multiple reviewers may be used where justified by risk, without a universal fixed vote count. A finite resolution budget ends in escalation, never automatic approval. Recovery can obtain missing operands, select a fresh baseline and rerun affected work, or return to planning. It preserves unresolved obligations and states the concrete prerequisites for re-entry. Resolved issues need new evidence to reopen.

## D6. Verification

Use the least costly checks sufficient for the claimed guarantees (P4). Fast development feedback and acceptance checks may have different scopes. A passing command is evidence about what it actually executed, not proof of all requirements. Independent review examines whether the tests can detect the important failures claimed. For material observable requirements, retain a concrete expected observation and plausible adverse input derived from the requirement separately from editable implementation; run the actual relevant consumer with healthy and adverse inputs. Changing the expected result is a changed verification premise and requires a demonstrated fixture defect or authorized requirement decision. Unobservable material premises need a named qualitative strategy and limits; an unavailable necessary oracle cannot be silently called a pass. For each important guarantee, explain the failure being detected and use the lowest sufficient test boundary. Real integration evidence is necessary when mocks omit the very behavior claimed; exhaustive end-to-end duplication is not required.

Match an evidence duty to its actual consumer. Recording an original baseline execution is a historical witness, not a fabricated pair of production-function cases. A complete file-scope comparison is an observable host predicate and retains actual healthy/adverse inputs. A finite mixed plan independently selects and reviews these typed strategies alongside behavioral cases; it neither erases requirements nor makes an author-selected qualitative waiver. Required evidence remains version-bound and unavailable when its original execution, complete inputs or independent acceptance cannot be established. Once independently accepted, typed accounting cannot disappear through replanning or serialization. Preserve historical before-edit duties without retrospective substitution; an unsupported cross-plan witness mapping stays unavailable. A small repair still needs current evidence and independent acceptance when no qualified typed judgment carry exists, and its extra executions consume the retained allowance.

Set and observe execution budgets for frequent feedback and acceptance verification. Budget overruns trigger diagnosis or an explicit revised verification plan, not silent omission of necessary tests. Targeted execution is allowed only with an explained coverage scope; unknown impact falls back to sufficient broader checks. No impact-analysis algorithm is mandated. Resource budgets include memory and bounded cleanup; timing-sensitive tests control fixture-owned processes and attribute failures to the intended assertion rather than any crash or timeout.

Document tests assert semantics where those semantics are product behavior. Hashing prose or freezing exact wording merely to preserve a document is not a correctness guarantee. Demonstrate important tests' sensitivity to relevant failures through proportionate evidence; mutation testing is one option, not a universal additional gate.

## D7. Records and resumption

Ordinary-owner admission recovery is a metadata transition separate from execution and authority recovery. Reuse original work discovery, bounded source/producer facts and shared-family settlement. An owner can restore a cancelled/interrupted independent root and withdraw a settled cancelled wait through exact review, archiving its scheduler state while retaining child/dependency obligations. Preserve work generation so the retained role-model source remains valid; advance epoch to keep prior authority stale. A later explicit input uses existing runtime/model/history gates. This action neither verifies physical history nor renews an integration grant.

Agent-level retains detailed planning, review rounds, adjudication, and retries. Repository-facing records summarize the change's intent, meaningful verification, review outcome, and acceptance authority. Resumption reconstructs state from retained evidence and actual current repository state, invalidating outdated conclusions. The supervisor captures a content-addressed immutable run input and requirement snapshot before dispatch; producer identity comes from its launch registry rather than a caller role label. Candidate identity includes the effective content reviewed or executed, not just a commit label: uncommitted and relevant generated inputs matter. Evidence retains dependency scope so unaffected conclusions can survive unrelated changes.

The controller retains one governed-work continuation identity separately from task/session/review execution identifiers and PR numbers. Managed origins and existing artifact bindings resolve predecessor checkpoints, open obligations, and consumed resolution allowance before a continuation starts. A managed replan or replacement PR carries that identity; renaming an execution cannot create an empty history or fresh allowance. Authorized supersession records changed scope/method, inherited obligation dispositions, and any bounded allowance extension. Genuinely independent work remains separately usable. Undisclosed out-of-band copies with no resolvable managed origin are an explicit coverage limit; this design does not require a global semantic clone detector.

A durable transactional ledger reserves the per-work operation identity, consumed allowance and eligibility epoch. Relevant local state changes advance the epoch; final dispatch compares current bound fields under that same serialization. Before an external action the controller refreshes relevant remote state and uses a candidate-conditional operation. A minimal Git transport adapter builds pinned integration I from reviewed H and base B, verifies affected integration and B ancestry, then conditionally updates the authorized branch using explicit expected-old B semantics. This requires native server permission and does not claim PR closure. Base drift requires a rebuilt and revalidated candidate. A hosting adapter must supply sufficient head/base conditions or a native integration queue for its claimed guarantees; a head-only API condition cannot stand in for base atomicity. Concurrent attempts on the same task are serialized. If an interrupted operation's result is unknown, reconcile actual state before retrying; uncertainty is not success or permission to repeat side effects. Machine-readable records retain their intended semantics through rendering, transport, and publication; user-facing text sanitation cannot rewrite their values. Publication failures or uncertain sends are reconciled before retry. Persist operation identity before send; replay requires confirmed absence or provider-supported idempotence. Ambiguous non-idempotent sends remain unknown with targeted recovery. Cancellation before invocation revokes eligibility; cancellation of an in-flight operation requires outcome reconciliation rather than assuming no effect. Prose publication adapters enforce the configured final-byte payload policy before send: notification carriers are disallowed by default unless explicitly allowed, prohibited control bytes and configured known private literals are refused. These checks are endpoint-scoped and preserve original authoritative data separately; they are not a universal secret/audience oracle. Unrecognized semantic private meaning remains subject to independent scrutiny and stated limitations. Consequential nonblocking observations and limits survive composition without becoming mandatory improvements. New reset manifests bind the exact selected root paths and the device, inode, type, owner and permissions of those roots and the stable home/state directories. Reset renames each approved root intact, including its current nested contents, without enumerating, counting or hashing payload files. Backup mode retains that private tree. Permanent deletion uses a separate private staging directory and a durable deleting phase before recursive removal; an interrupted deletion continues only for the same staging identity. Existing backups remain separately managed. Preview consent covers those namespaces rather than a byte snapshot. Recovery checks the original or backup root identity and refuses replacement, unexpected active roots or simultaneous source and backup copies. Internal content changes remain preserved in the moved root. Legacy full-inventory, content-commitment and root-only manifests retain their original backup recovery proof. Completed backups expose metadata-only discovery and separately confirmed deletion. Its inactive-data journal can resume partial removal without blocking ordinary application startup; conflicting maintenance remains held until that journal settles. The manifest and completion receipt must fit their storage bound before preview succeeds. Historical backups are outside the active runtime census; reset does not certify old software, refund allowance in an original lineage, revoke platform credentials, or erase external effects. A fresh active store establishes new local records only after original execution cleanup is settled.

Completion review separates private source capture from its model-facing presentation. A bounded frozen capsule presents current selected facts once, while private fingerprints retain original raw sources and the exact selected records behind those facts. Recompute those sources at acceptance rather than comparing a formatted projection with raw rows or hashing only the already-frozen capsule. This keeps large histories usable without weakening drift detection or granting a reviewer new access merely because it is a reviewer.
